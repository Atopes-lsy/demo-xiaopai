## 3. 变量：E1b-1

| 组别 | max_tokens | 其他参数 |
|---|---:|---|
| 控制组 C | `2000` | 与第 2 节完全一致 |
| 变量组 V1 | `1200` | 与第 2 节完全一致，只改 max_tokens |

> 先核对控制组的真实运行环境：如果 E1b 在 Coze 主图上执行，控制组和变量组都用 Coze 托管配置（当前记录 temp `0.0`）；如果用火山方舟脚本执行，控制组和变量组都用同一脚本和同一 temperature。**不能控制组用 Coze 托管、变量组用直连脚本，也不能拿 E0 的 21 次直连数据当本工单控制组。**

**先判断这个变量是否可能生效。** `max_tokens` 是生成上限，不是目标长度：

- 如果控制组 21 次输出的 token 数（或字符数换算）都明显低于 1200，且没有截断，那么把上限从 2000 降到 1200 很可能**不会改变延迟**。
- 这种情况下如实记录“该参数未触及生成上限”，不要为了证明实验有效而继续降参数。
- 只有在控制组存在接近上限、输出过长或截断时，E1b-1 才具备明确的降延迟假设。

> 本次实际结果是另一种失败：两组都有超过各自上限的输出且 `finish_reason=stop`，说明上限根本没有绑定请求。详见第 9 节；这比“输出低于上限”更严重，不能继续降参数。

- `max_tokens 800`：等 T3 压缩 `notes` 后再单独实验；
- `temperature` 调整：另开实验，不能和 E1b-1 同时跑；
- 换模型：E1a 已关闭；
- 关闭 JSON 模式：下游依赖，不允许。

## 4. 测量口径

控制组和变量组必须使用**完全相同**的测量方法：

1. **优先**：Coze 日志中抽取 LLM 节点的耗时（node latency）。
2. **如果拿不到节点耗时**：用同一个外部脚本测整个工作流耗时，并明确标注为 `end-to-end`。
3. 不允许控制组用节点耗时、变量组用端到端耗时；也不允许中途换脚本。
4. 每组 7 条 × 3 次 = 21 次；记录每一次，不删异常值。异常值单独标注，不静默丢弃。
5. 统计 median 和 p95，使用同一脚本；21 个样本只作方向性判断，不写“统计显著”。

每次运行至少保存：

```text
exp, item_id, run, input_present, latency_ms, latency_scope,
finish_reason, prompt_tokens, completion_tokens, output_chars,
events_cnt, status, predicted_events, notes, error
```

如果 Coze 不显示 token 数，`prompt_tokens`/`completion_tokens` 留空，但必须记录 `output_chars` 和是否截断。

6. 控制组的 7×3 全流程延迟可补齐主回归的逐次记录，但它**不能**补齐 E0 的 21 次抽取节点同口径延迟；后者若仍需要，另做同渠道抽取节点测量。

控制组质量检查：

- 输入传入：21/21；
- JSON 可解析、无截断：21/21（已知 P1 类 JSON 问题要单独标注，不得混入“参数导致截断”）；

如果控制组本身没有达到上述条件，先修复或记录偏差，**不要进入变量组**。

### 第 3 步：只改 max_tokens

1. 抽取 LLM 节点 `max_tokens: 2000 → 1200`。
2. 其他参数逐项核对：模型、temperature（以控制组实际值为准；本次直连脚本为 `0.1`）、JSON 模式、Prompt、节点接线均未变。
3. 保存修改前后截图或参数 diff。
4. 建议先单独跑 1 条冒烟测试，确认能正常返回完整 JSON；这次不计入 21 次统计。

### 第 4 步：跑变量组 V1（max_tokens 1200）

1. 使用与控制组完全相同的 7 条输入、顺序、基准日和运行方式。
2. 每条 3 次，共 21 次；按第 4 节字段记录。
3. 不要因为某次输出看起来更短就手动补字段；记录模型原始输出。
4. 运行完成后检查是否截断、是否 JSON 损坏、是否丢字段。

### 第 5 步：评分与对比

按同一套标准逐条评分，至少覆盖：

- 输入是否传入；
- JSON 是否完整可解析；
- 事件级是否正确（漏事项/多事项）；
- 时间、地点、类型、优先级是否正确；
- deadline 是否仍正确（id 7/id 8 必须 3/3）；
- 幻觉是否新增；
- 隐含 task 是否超过 1 条；
- id 4 周次歧义是否仍写出。

对比控制组和变量组：

- 质量：变量组不得引入新的失败项；id 7/id 8 不得退化。
- 延迟：报告 median、p95 和逐条差值；判断是否由个别长尾驱动。
- 若变量组只快在 1–2 次、median 基本不变，记录“无实质收益”，不采用。

### 第 6 步：负例安全检查

采用前，用 E0.1 的 N1–N4 各跑 1 次，确认 max_tokens 调整没有引入 deadline 误抽。这 4 次不计入 21 次延迟统计，但必须记录结果。

### 第 7 步：决定采用或回退

**采用条件（全部满足）：**

- 21/21 输入传入；
- 21/21 JSON 可解析，无截断；
- 事件级、时间、地点、优先级、幻觉均不比控制组差；
- id 7/id 8 deadline 均 3/3；
- 无新增多抽；
- N1–N4 无新增 deadline 误抽；
- median 延迟有下降，且不是由单条异常值驱动；
- p95 没有明显恶化。

如果所有输出都远低于 1200 tokens，参数变更没有实际效果，也应判定为“不采用/无效实验”，不要写成“优化成功”。本次更直接：输出超过上限且正常结束，说明参数未绑定，详见第 9 节。

**回退条件：出现任一质量退化、截断、deadline 失败或负例误抽，立即恢复 `max_tokens=2000`。**

## 8. 常见错误

- **拿 v3 的 27.2 s 直接对比 E1b。** 不可以。Prompt 已变成 v3-opt+E0.1，测量口径也可能不同；只能比较本工单的控制组和变量组。
- **控制组没归档就开始改参数。** 不可以，后面没有可比基线，也补不上主回归证据。
- **把现有 7×1 主回归当成 7×3 控制组。** 它只有 1 轮/条，且是全流程口径；E1b 需要 21 次同条件控制数据。
- **把全流程延迟说成抽取节点延迟。** 7 次主回归的 median 11040 ms 是 `main_graph.invoke` 全流程；E0 的 21 次主口径约 27.2 s 是仅抽取节点，不可横比。
- **控制组和变量组渠道/温度不一致。** 例如控制组 Coze 托管 temp 0.0、变量组直连脚本 temp 0.1，结论作废。
- **把 `events_cnt=0` 直接算作空输出。** 先看完整 raw；历史上已有 JSON 损坏导致计数为 0 的情况。
- **一次改多个参数。** 延迟变化无法归因，实验作废。
- **把目标值写成结果。** 没有实测就写“待测/未执行”。
- **上传原始通知、真实校名/老师名或截图。** 只使用脱敏后的 7 条。
- **max_tokens 远高于实际输出却继续降。** 先确认参数是否触及生成上限；没触及时应停止，而不是制造“优化”结论。

### 9.1 实际条件

- 渠道：火山方舟直连脚本，不是 Coze 主图托管；两组使用同一脚本、同一 Prompt（v3-opt + E0.1 补丁）。
- 模型：`doubao-seed-2-0-pro-260215`，非推理，thinking disabled。
- temperature：`0.1`（两组一致）。
- 其他：JSON 模式开启；测试基准日 `2026-10-18 09:00`；7 条 × 3 次，串行；`latency_scope=extract_llm_e2e`。
- 输入：42/42 次 `input_present=1`；42/42 次 `status=ok`；42/42 次 `finish_reason=stop`。
- 数据：[控制组](../06-研究发现/coze测试数据/v3/v3.3/e1b1_control_max2000.csv)、[变量组](../06-研究发现/coze测试数据/v3/v3.3/e1b1_variant_max1200.csv)、[完整记录](../06-研究发现/coze测试数据/v3/v3.3/README.md)。

> 这次执行符合“两组必须同渠道”的要求，但仍不是 Coze 主图 temp `0.0` 的生产路径；结论不能直接套用到主图。

### 9.2 结果

**操纵检查（先于任何效果判断）**

| 组别 | 设定 | 超过设定值的运行 | 最大 completion_tokens | finish_reason |
|---|---:|---:|---:|---|
| C | 2000 | 4/21 | 3085 | 全 `stop` |
| V1 | 1200 | 19/21 | 2909 | 全 `stop` |

两组均有超过各自上限的输出且正常结束，说明 `max_tokens` 没有实际约束生成；C/V1 很可能实际是同一有效配置。**这是操纵失败，不是“max_tokens 无效”的干净结论。**

**质量（主事项是否抽出）**

- C：18/21；失败为 id 2 run1、id 7 run2、id 7 run3（均为 0 事件）。
- V1：20/21；失败为 id 7 run1（0 事件）。
- id 7：C 1/3、V1 2/3，合计 3/6；id 8 两组均 3/3。
- id 4 周次歧义：两组共 6/6 都写出 `2026-10-22` 与 `2026-10-29`；与 7×1 主图 temp 0.0 的缺失相反，是温度假设的反向信号。
- 多抽：按“主事项 + 最多 1 条隐含 task”口径为 0；原始 `events_cnt=2` 在 C 有 3 次（id 2 run2/3、id 7 run1），V1 有 5 次（id 2 ×3、id 7 ×2）。严格“恰好 1 事件”口径需另算。
- 负例：仅 V1 的 N1–N4 各跑 1 次，0/4 误抽；**控制组负例未运行**。

**延迟**

| 分组 | n | 平均 (ms) | 中位 (ms) | p95 (ms) | 最小 (ms) | 最大 (ms) |
|---|---:|---:|---:|---:|---:|---:|
| C 全部 | 21 | 37911.7 | 34947 | 66866 | 8920 | 69690 |
| V1 全部 | 21 | 35861.9 | 36278 | 46386 | 7853 | 59747 |
| C 非空 | 18 | 42141.1 | 36198 | — | 26731 | 69690 |
| V1 非空 | 20 | 37262.3 | 36418.5 | — | 22603 | 59747 |

全部运行中位数 V1 比 C 慢约 1.3 s；非空输出中位数差约 0.2 s。没有中位数收益；p95 差异由 C 的少数长尾和 21 样本的不稳定性驱动，不能写成 V1 降低尾延迟。由于操纵失败，以上延迟差不能归因于 max_tokens。

### 9.3 决定

- **不采用 1200；维持 2000。** 这是“不做无依据的配置变更”，不是实验证明 2000 最优。生产配置未改，无需回退动作。
- **不执行 E1b-2（800）**，直到确认参数能真正绑定请求并制造截断。
- 质量 20/21 vs 18/21 是重复运行噪声，不能写“V1 更好”；id 7 的 3/6 是后续观察信号，不是温度结论。
- 控制组未达到本工单第 2 步的 id 7 3/3 质量门，变量组仍被运行；因此即使忽略操纵失败，本次也不满足采用条件。

### 9.4 与工单要求的偏差

1. 在火山方舟直连 temp `0.1` 执行，不是 Coze 主图 temp `0.0`；两组同渠道成立，但不能直接代表主图。
2. 控制组 id 7 只有 1/3，未通过控制组质量检查就进入了变量组；本次只能作探索性数据。
3. 负例只跑了 V1 一侧，控制组 N1–N4 未跑；不能写“两组负例均零误抽”。
4. 没有记录到正式的小上限冒烟验证，导致 21×2 次跑完后才发现 max_tokens 未生效。
5. 质量只对主事项是否抽出做了逐次复核；时间、地点、类型、优先级的完整字段级评分未单独落表。
