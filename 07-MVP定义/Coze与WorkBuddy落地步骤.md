# Coze 与 WorkBuddy 落地步骤：小排

> **2026-10-18 产品转型说明**：产品已更名为「小排」，核心从「课表 + 群通知识别」改为「项目/消息 → 任务/DDL → 自动排期 → 今日待办」。课表降为次要能力，MVP 不做每日提醒。本文的抽取测试方法继续可用；示例中的“课表”场景请按新 PRD 替换。抽取 schema 以 [`PRD-v0.1.md`](../08-PRD/PRD-v0.1.md) 9.8 和 [`coze_prompt.md`](../06-研究发现/coze测试数据/v1/coze_prompt.md) 为准；本文早期 prompt 若缺 priority/estimate/dependencies，以新 prompt 为准。
>
> 目标：用这两个工具把「研究 → PRD → 原型 → 抽取验证 → 2–3 人 pilot」跑起来，而不是多学两个平台。
>
> 前提：它们只负责“做出来”和“跑起来”，不替代真实用户证据；AI 生成的数字、用户原话、研究结论，必须由你核对。

---

## 0. 先分工：谁做什么

| 工具 | 本质 | 在本项目里做什么 | 不做什么 |
|---|---|---|---|
| **WorkBuddy**（腾讯） | AI 办公智能体 / 专家团，偏“交付物” | 生成 PRD 骨架、可点击 HTML 原型、流程图、字段字典、访谈/竞品整理、面试故事 | 不生产用户证据；不替代 Figma 精细设计；不直接做微信小程序 |
| **Coze / 扣子**（字节） | 零代码智能体 + 工作流平台，偏“流程” | 搭「通知 → 抽取 → 结构化卡片」工作流；做测试版 Bot；跑现有 7 条真实通知准确率；可选发布到微信客服 | 不替代「长按转发」真机验证；不是正式后端；发布微信客服需要企业认证 |
| 飞书多维表格 / 腾讯文档 / 简道云 | 表单、台账、看板 | 访谈库、反馈池、问卷回收、pilot 记录 | 不做 AI 抽取 |

一句话：**WorkBuddy 做“给人看的文档和原型”，Coze 做“给机器跑的抽取流程”，真实用户和微信入口仍然要你自己验证。**

---

## 1. 三天最小落地顺序

| 时间 | WorkBuddy | Coze | 产出 |
|---|---|---|---|
| Day 1 上午 | 导入材料，生成 PRD 骨架 | 建 `notice_extract_v0` 工作流 | `PRD-v0.1.md`、工作流 v0 |
| Day 1 下午 | 生成「粘贴 → 确认 → 排期 → 今日」的 HTML 原型 | 用现有 7 条真实消息调 prompt | 可点击原型、抽取 v1 |
| Day 2 上午 | 人工校对 PRD 和原型 | 用 7 条真实通知多轮复测，记录指标 | 测试 CSV、错误清单 |
| Day 2 下午 | 准备 pilot 脚本和记录表 | 建 Bot，生成分享链接 | Bot 链接、pilot 脚本 |
| Day 3 | 用原型 + Bot 跑 2–3 人 pilot | 按错误改 prompt v2 | pilot 记录、PRD v0.2 |

如果只有 1 天：只做 Coze 工作流 + 7 条通知 + 1 个朋友；PRD 和原型先用文字/低保真替代。

## 2. WorkBuddy 落地步骤

### 2.1 准备输入（30 分钟）

先把材料放进一个文件夹，**全部脱敏**：删掉真实姓名、学号、手机号、群名、学校全称，用“同学 A / 某学院 / 某课程群”代替。

需要准备：

- `README.md`
- `01-问题假设/prd前研究流程.md`（H1–H10）
- `02-竞品与替代方案研究/` 的竞品结论
- `03-用户访谈/` 的访谈原话（至少 1 份）
- `04-用户问卷/` 的题目和回收结果（如果有）
- `05-技术与合规调研/` 里的微信能力结论、AI 识别测试方案、合规边界
- `07-MVP定义/低代码原型与内部工具方案.md`

### 2.2 生成 PRD 骨架（1–2 小时）

1. 打开 WorkBuddy（网页版或桌面端，以当前版本为准），新建项目/工作空间；
2. 选择“产品经理 / 需求分析 / MVP”类专家或 Skill。**优先用官方或可核验来源的 Skill**，社区 Skill 先看发布者、权限和输出示例；
3. 上传或粘贴材料；
4. 用下面的 prompt 生成 PRD；
5. 生成后不要直接用，按 2.6 的清单逐项校对。

**PRD prompt（可直接改）：**

```text
你是「小排」项目的产品经理。基于我提供的材料，输出 PRD v0.1。

项目背景：微信小程序「小排」。用户把微信/QQ 群消息、项目说明或待办粘贴进来，
AI 拆成任务/日程/DDL，按截止时间、优先级、空闲时间自动排进日历；
用户确认/拖拽后保存。课表导入是次要能力；MVP 不做每日提醒。

必须遵守：
1. 每个研究发现都要标注证据来源（访谈/问卷/竞品/官方文档）；没有证据的写成“待验证假设”，
   禁止编造用户原话、样本量、比例。
2. 微信能力按以下边界写，不许夸大：
   - 主入口是粘贴，不依赖长按转发；
   - 后续若做转发/客服，单条、合并转发仍需真机验证；
   - 订阅消息按一次性额度设计，不承诺长期自动提醒；
   - 微信客服 48 小时内最多发 5 条。
3. 输出结构：
   背景与个人问题来源 / 目标用户 / 用户问题 / 产品定位 / 目标与指标 /
   MVP 范围（必做、暂不做）/ 用户流程 / 功能需求与验收标准 /
   任务、日程、DDL 的数据结构 / 自动排期规则 / 提醒规则（V1）/
   今日视图 / 识别失败与模糊时间处理 /
   技术依赖与限制 / 隐私与合规 / 埋点 / 风险与开放问题。
4. 不确定的地方列“待确认”，不要替我做决定。
5. 中文 Markdown，具体、可开发；不要写空泛的“提升体验”。

我提供的材料如下：
[粘贴材料或说明文件已上传]
```

生成后追加一轮：

```text
请列出这份 PRD 中所有“没有证据支撑的断言”，按风险从高到低排序，
并给出每条的最小验证方法（访谈问题/问卷题/真机测试/数据测试）。
```

### 2.3 生成可点击 HTML 原型（1–2 小时）

用途：给 2–3 个同学点，验证“看不看得懂、愿不愿意用”，不是最终小程序。

**原型 prompt：**

```text
做一个单文件 HTML 移动端可点击原型，产品名「小排」，宽度 375px，中文。

页面与状态：
1. 首页/今日：今日排期时间线；顶部「临近 DDL」；逾期标红；
   显著入口「粘贴一条消息/项目」；底部 tab：今日 / 日历 / 项目 / 我的。
2. 粘贴输入：多行文本框、读取剪贴板按钮、示例文本；来源标记（微信/QQ/其他）。
3. 确认卡片：一条输入可拆成多个事项；每个事项展示标题、类型（任务/日程/DDL）、
   时间、截止、地点、优先级、预计时长、置信度；字段可编辑；
   低置信度显示「请确认」；可删除/合并；按钮：下一步。
4. 排期预览：日历 + 列表；每个任务块显示「为什么排在这里」；
   可拖拽、可锁定；排不下的任务给「延长可支配时间 / 减少估时 / 拆任务 / 顺延 / 放弃」。
5. 今日视图：完成/开始/顺延；保存成功页 + 任务详情页。
6. 空状态、解析失败、排期失败各一个。

交互要求：
- 粘贴 → 确认 → 排期 → 今日，能完整点通；
- 用 mock 数据，不接后端；
- 页面顶部标注「原型，数据为示例」；
- 无外部依赖，浏览器直接打开；适配手机；
- 不做登录、支付、社区、复杂动画；
- 课表入口只放在「我的/更多」，不作为首页核心。

请输出完整 HTML 文件，并附一段「如何演示」的 6 步说明。
```

生成后自己先点一遍：首页 → 导入 → 确认 → 保存 → 回首页。截 3 张图放进 pilot 记录。

### 2.4 生成流程图、信息架构、字段字典（可选，1 小时）

```text
基于上面的 PRD，输出：
1. 用户主流程图（Mermaid flowchart）：粘贴消息/项目 → 抽取 → 确认 → 自动排期 → 今日；
2. 信息架构：今日、日历、项目、任务详情、确认卡片、设置；
3. 数据字段字典：任务/日程/DDL/排期块，字段名 / 类型 / 是否必填 / 来源 / 示例 / 校验规则；
4. 状态机：任务、日程、DDL 各自的状态与异常路径。
标注所有“识别失败、时间模糊、地点缺失、重复提交”的分支。
```

### 2.5 用 WorkBuddy 整理研究证据（30 分钟）

```text
把下面的访谈记录整理成表格：
原话/行为 / 对应假设（见 PRD 2.4）/ 证据强度（强/中/弱）/ 结论 / 产品影响。
要求：
- 没有证据的不要补；
- 写清楚样本量（例如“1 名受访者”）；
- 区分“用户说的”和“用户做的”；
- 最后列出 3 个最需要补验证的假设。
```

### 2.6 PRD / 原型校对清单

- [ ] 每条研究发现有来源，没有编造的数字或原话；
- [ ] 区分了“事实”和“待验证假设”；
- [ ] 写清了主入口是粘贴、MVP 不做每日提醒、课表 P2、V1 提醒渠道限制；
- [ ] MVP 有明确的“暂不做”；
- [ ] 每个功能有验收标准，不只是描述；
- [ ] 有异常分支：识别失败、时间模糊、地点缺失、重复提交；
- [ ] 有数据模型和字段字典；
- [ ] 有隐私告知、原文删除、权限边界；
- [ ] 埋点能对应到指标；
- [ ] 没有上传真实姓名、手机号、学号、群名等个人信息；
- [ ] 原型能完整点通，不是静态截图；
- [ ] 原型明确标注“示例数据 / 非最终产品”。

### 2.7 WorkBuddy 常见坑

- **AI 会“写得很完整”，但不一定对。** 特别是用户比例、访谈原话、竞品结论，必须回到原始材料核对；
- **社区 Skill 不是官方能力。** 安装前看来源和权限，不要授予不必要的文件/网络访问；
- **HTML 原型不是 Figma。** 用在概念测试、可用性测试足够；如果面试要求 Figma，再用它做低保真复刻；
- **不要上传原始聊天记录。** 先打码，或只粘贴结构化摘录。

## 3. Coze 落地步骤

### 3.1 先做哪条链路

第一版只做**文字输入**：

```text
用户粘贴一条群消息 / 项目说明 / 待办
→ Coze 工作流
→ 意图判断（是否包含可安排事项）
→ 否：回复使用说明/追问
→ 是：LLM 抽取任务/日程/DDL（含截止、优先级、估时）
→ 代码节点校验
→ 返回确认卡片
→ 自动排期由小程序/后端规则引擎完成（Coze 不负责排期）
```

图片/截图识别、转发解析先不做；它们要等多模态和微信真机验证。Coze 只做抽取，不要把排期逻辑塞进工作流。

### 3.2 建工作流（1–2 小时）

> 完整可复制版本（含意图/抽取 Prompt、两个代码节点、测试用例、Bot 提示词）见 [Coze-小排工作流提示词.md](Coze-小排工作流提示词.md)。下面保留最小版本；字段口径（`estimate_min`、event 优先级、时间格式）以完整版为准。

1. 打开 [coze.cn](https://www.coze.cn)，进入工作空间；
2. 新建工作流，命名 `notice_extract_v0`；
3. 开始节点加两个入参：
   - `notification_text`：通知原文；
   - `current_date`：当前日期（`YYYY-MM-DD`）；
4. 加意图判断节点：用轻量 LLM 输出 `has_recordable_event`、`intent_confidence`、`reason`；
5. 加条件节点：`has_recordable_event = false` 时走结束节点，回复使用说明；为 true 时进入抽取；
6. 加 LLM 抽取节点，模型选你账号可用的国内模型，temperature 设 0–0.3；
7. 加代码节点，解析并校验 JSON；
8. 加结束节点，输出 `result_json`、`needs_confirmation`、`error`；
9. 用 3 条通知 + 3 条闲聊试跑，确认通知能出 JSON、闲聊不生成记录。

**意图判断节点 prompt：**

```text
你是「小排」的输入分流器。判断用户消息是否包含需要记录的日程、DDL 或任务。
只输出严格 JSON，不要 Markdown 代码块：
{
  "has_recordable_event": true/false,
  "confidence": 0.0,
  "reason": "一句话理由"
}

规则：
1. 闲聊、问用法、感谢、表情、与安排无关的内容 → false。
2. 包含时间、地点、截止日期、需要完成的事 → true。
3. 不确定时倾向 true，交给抽取节点和用户确认，避免漏记。
```

**LLM 节点 prompt：**

```text
你是「小排」的消息/项目抽取器。输入是用户粘贴的微信/QQ群通知、项目说明或待办原文。
只做信息抽取，不回答问题，不补充原文没有的信息。

当前日期：{{current_date}}
通知原文：
{{notification_text}}

输出严格 JSON，不要 Markdown 代码块，不要解释：
{
  "events": [
    {
      "title": "活动/事项名称，没有则 null",
      "type": "task | event | deadline | unknown",
      "start_time": "YYYY-MM-DD HH:mm 或 null",
      "end_time": "YYYY-MM-DD HH:mm 或 null",
      "deadline": "YYYY-MM-DD HH:mm 或 null",
      "location": "原文中的地点，没有则 null",
      "priority": "P0 | P1 | P2 | P3 | null",
      "estimate_min": 0,
      "dependencies": [],
      "confidence": 0.0,
      "missing_fields": ["time", "location", "title"],
      "evidence": "原文中最能支持该事件的短句",
      "ambiguity": "模糊时间/多个时间/需要用户确认的点，没有则 null"
    }
  ],
  "needs_confirmation": true,
  "notes": "整体不确定点，没有则 null"
}

规则：
1. 一条输入可能包含多个事项，拆成多个 events。
2. 任务 task = 需要投入时间完成；日程 event = 固定时间参加；
   DDL deadline = 某时前完成/提交；无法判断用 unknown，不要硬猜。
3. 相对时间（明天、下周三、本周五）按当前日期解析；无法解析就保留原文到 ambiguity，
   对应时间字段用 null。
4. 原文没有的地点、时间、截止一律 null，禁止推测。
5. confidence 表示该事件整体可确认程度；低于 0.7 时 needs_confirmation = true。
6. 只有日期没有具体时间：start_time 写日期 + 00:00 是不允许的，保留日期、时间部分写 null，
   并在 ambiguity 说明。
7. evidence 必须是原文短句，不能改写。
8. priority 只在有明确线索时给：P0 = 24 小时内截止/不可延期，P1 = 7 天内截止/重要，
   P2 = 普通，P3 = 有空再做；不确定用 null。
9. estimate_min 只在原文明确写了时长时填写（如“预计 2 小时”=120）；
   没写就填 0，不要猜；排期时由后端用默认估时。
10. dependencies 只在原文明确表达先后关系时填写；否则空数组。
```

**代码节点做什么：**

```text
1. JSON.parse(raw)；失败则返回 { ok: false, error: "invalid_json", raw }；
2. 检查 events 是数组；每个 event 补齐字段；
3. 根据 missing_fields 和 confidence 重新计算 needs_confirmation；
4. 返回 { ok: true, data, needs_confirmation }。
```

> 代码节点语言按当前版本支持的选择（JS/Python）；变量引用方式以当前版本为准。

### 3.3 建测试 Bot（30 分钟）

1. 新建 Bot，命名“小排通知助手（测试版）”；
2. 绑定 `notice_extract_v0` 工作流；
3. 系统提示词如下；
4. 在 Coze 调试台用现有 7 条通知测试；
5. 生成分享链接/二维码。

**Bot 系统提示词：**

```text
你是「小排」的测试版通知整理助手。

- 用户发来一条群消息/项目说明/待办后，调用 notice_extract 工作流，不要自己编造时间、地点、截止日期。
- 回复一张简洁卡片：类型 / 标题 / 时间 / 截止 / 地点 / 优先级 / 预计时长 / 置信度。
- 时间或地点缺失、置信度 < 0.7 时，明确说“需要你确认或补充”，不要猜。
- 不保存原文；不询问与整理无关的隐私信息。
- 开头说明：这是测试版，内容只用于本次整理，整理完可删除。
- 用户确认后回复“已记录（测试）”。
- 不承诺自动提醒；订阅消息额度有限。
- 如果意图判断为 false，回复使用说明，不要自己抽取；如果用户只是问用法，告诉他怎么发通知。
```

**卡片格式示例：**

```text
【任务】课程报告初稿
截止：2026-10-23 23:59
预计：90 分钟
优先级：P1
置信度：0.82

请确认：截止时间、预计时长是否正确？
```

### 3.4 用现有 7 条真实通知跑评测（半天）

数据来源：你自己的班群/社团群/课程群，或同学转发；**全部打码**，不要保留真实姓名、手机号、群名。当前只有 7 条，先按「通过条数 / 7」记录，不把结果写成总体准确率。

下面的覆盖类型是扩样目标；现有 7 条以单事项群通知为主，项目说明、多事项拆分、模糊时间等尚未覆盖：

- 单事件，有明确时间 + 地点；
- 单事件，只有时间没有地点；
- 一条通知多个事件；
- 项目说明，包含多个任务、截止时间和先后关系；
- 相对时间（明天、下周三）；
- DDL（交材料/报名截止）；
- 日程 vs DDL 容易混淆；
- 模糊时间（“下午”“课后”）；
- 长通知，含大量无关内容；
- 没有时间的通知；
- 图片/截图（第一版可先不做，单独记录）；
- 另加 5–10 条闲聊/问用法，验证意图判断不会误抽。

记录 CSV 建议字段：

```text
id, raw_text, expected_events, predicted_events, event_match,
intent_ok, time_ok, location_ok, type_ok, priority_ok, estimate_ok, dependency_ok, hallucination, latency_ms, notes
```

指标：

- JSON 合法率；
- 意图判断准确率（含事项/纯闲聊是否分对）；
- 事件级准确率；
- 时间准确率；
- 地点准确率；
- 类型（任务/日程/DDL）准确率；
- 优先级准确率（原文有明确线索时）；
- 估时准确率（原文明确写了时长时）；
- 依赖关系准确率（原文明确写了先后时）；
- 幻觉率：原文没有、模型编出来的时间/地点/截止/事件；
- 延迟；
- 人工修正时间。

参考通过线（按 `05-技术与合规调研/AI识别准确性测试方案.md` 的最终标准）：

- 意图判断 ≥ 90%；
- 事件级 ≥ 80%；
- 地点 ≥ 80%；
- 优先级 ≥ 70%（只统计原文有线索的）；
- 幻觉 < 5%；
- 达不到就继续改 prompt / 加规则，不要直接进入正式开发。

### 3.5 2–3 人 pilot（半天）

不要叫“用户验证 10 人”，就叫 **pilot**。

**邀请话术：**

```text
我在做一个把群消息/项目任务自动排进日历的助手。你最近收到的群通知或项目任务里，
能不能挑 3 条发给我？我会回一张卡片并给个排期，你帮我看看有没有用。
大概 10 分钟，内容我会打码，测完删除。
```

**记录表：**

| 日期 | 测试者 | 身份 | 输入条数 | 完成时间 | 修改了哪些字段 | 排期是否拖拽/为什么 | 是否愿意继续用 | 原话 | 备注 |
|---|---|---|---|---|---|---|---|---|---|
|  |  | 作者自测 / 外部用户 |  |  |  |  |  |  |  |

**观察重点：**

- 用户是否知道要发什么、怎么发；
- 用户更愿意粘贴通知，还是直接说一句要记的事；
- 卡片上的信息是否够用；
- 哪个字段最常被改；
- 用户是否接受自动排出的时间；拖拽/放弃的原因；排不下时选了什么；
- 用户是否愿意再发第二条；
- 用户最担心什么（隐私、识别错、排得不准、麻烦）；
- 用户是否会主动问“什么时候能用”。

**作者自测和外部用户分开写。** 不要把自己伪装成第二个外部用户；如果你只有 1 个朋友，就写“N=2 pilot（1 作者自测 + 1 外部用户）”，结论只写初步信号，不写比例。

### 3.6 可选：发布到微信客服（有企业主体再做）

> 新主入口是「小程序内粘贴」；微信客服转发只作为后续可选输入，不作为 MVP 验收。

适合：你已经注册企业微信、开通微信客服、完成企业认证，想验证“用户真的在微信里发消息”的链路。

大致步骤：

1. 在微信客服后台拿到企业 ID、Token、EncodingAESKey；
2. 在 Coze 的「发布 → 微信客服」里填配置，复制 webhook 地址；
3. 回微信客服后台配置回调地址；
4. 复制 secret 和客服账号，回 Coze 保存并发布；
5. 用另一个微信号发消息测试；
6. 记录：能否收到、回复延迟、长按转发是否保留完整内容。

注意：

- 发布到微信客服需要**企业认证**；学生项目先用 Bot 分享链接测试，不要一上来搭企业客服；
- 如果企业微信侧已启用微信客服，可能和 Coze 的接入冲突，先小号测试；
- **Coze 只能接住发到微信客服的消息，不能替你验证“长按转发”是否把完整内容送达**；这仍要真机抓 `sync_msg`；
- 客服 API 有 48 小时/5 条限制；不要把 Coze 当正式客服系统；
- 用户转发的内容含个人信息，必须告知、打码、限期删除。

### 3.7 Coze 常见坑

- 模型不按 JSON 输出：降低 temperature、加“只输出 JSON”、用代码节点兜底；
- 闲聊被抽成记录：先做意图判断；不确定时先追问，不要直接建记录；
- 意图判断误杀通知：规则倾向 true，让抽取节点和用户确认兜底；
- 工作流变量没传进去：先用固定样例测试，再接入 Bot；
- 免费额度/模型额度有限：先小样本跑通，再批量；
- 多模态图片识别不稳定：第一版只做文字；
- 把 Coze demo 当成“需求已验证”：它只能证明流程能跑，不能证明用户愿意用；
- 不要上传真实聊天记录和用户个人信息到第三方平台。

## 6. 什么算“落地成功”

- [ ] WorkBuddy 生成的 PRD 没有编造的用户数字/原话；
- [ ] PRD 明确写了微信能力限制和“暂不做”，并写明「MVP 不做每日提醒」「课表 P2」；

- [ ] 至少跑过 2 个真实测试者（1 个可以是作者自测，但要标注）；

- [ ] 没有把个人信息上传到第三方工具；
- [ ] 没有把 demo 说成“正式产品”或“需求已验证”。

## 7. 面试怎么讲（3 分钟版）

1. **为什么用这两个工具**：WorkBuddy 把研究和假设快速变成 PRD 和可点击原型；Coze 把“消息/项目 → 结构化事项”做成可测试的工作流，不用等开发；
2. **怎么做**：先人工定义抽取 schema 和异常规则，再用 Coze 跑 7 条真实输入多轮复测，按通过条数记录事件/时间/地点/类型/优先级准确率和幻觉率（只讲信号，不讲总体比例）；
3. **怎么验证**：用 WorkBuddy 原型 + Coze Bot 跑 2–3 人 pilot，重点看“愿不愿意粘贴、接不接受自动排期、拖拽/放弃的原因”；
4. **边界**：MVP 主入口是粘贴，不做每日提醒；V1 再验证服务号/订阅消息；Coze 发布微信客服需要企业认证；这些都不夸大；
5. **结论**：工具让验证变快，但不能代替用户证据；样本小就只讲信号，不讲比例。

一句话：**WorkBuddy 负责“做出来”，Coze 负责“跑起来”，你负责“判断值不值得做”。**
