# AI 识别准确性测试方案

## 为什么先测这个

产品最核心的差异化是：从一条群通知里抽出**活动名、时间、地点**，并判断它是**日程**还是 **DDL**。竞品研究把这件事列为 H7 的“真空白”，但空白不等于可行。如果大模型在实际班群通知上的字段准确率低于用户可接受阈值，整个核心钩子就不成立，PRD 必须退回“只识别日期和标题、地点二期做”。

本方案的目标不是“跑一个 demo”，而是产出一份可复现的证据：**在 30–50 条真实通知上，各字段准确率是多少、错在什么地方、用户要花多久改**。

---

## 1. 测试范围

### 本轮必测（文本通知）

- 单条消息里只有 1 个事件
- 单条消息里有 2 个及以上事件（若合并转发不可用，这是多条目录入的唯一路径；合并转发能否解析待真机验证）
- 相对时间：“下周四下午”“明天上午”“本周五前”
- 节次时间：“第 3-4 节”“周三 5-6 节”
- 地点：“A301”“教学楼 302”“线上腾讯会议”
- DDL：“周五前交”“下周一之前提交”“截止到 10 月 20 日 18:00”
- 模糊时间：“下午晚些时候”“课后”
- 无地点、无明确时间、长消息、错别字、emoji、通知截图转文字后的噪声

### 本轮不测（另开测试）

- 课表文件导入（Excel/PDF/图片）——见第 7 节
- 语音、位置消息
- 多语言
- 图片通知的 OCR 识别（可先用人工转写文本跑通抽取，再单测 OCR）

---

## 2. 数据集怎么来

### 样本量

- **第一轮：30 条**真实通知，覆盖上述类型，每类至少 3 条。
- **第二轮（留出集）：另外 20 条**，不参与 prompt 调优，只用于最终验收。
- 来源：自己和同学的真实班群/社团群通知；取得对方同意；**去掉姓名、学号、手机号、具体宿舍号**等个人信息，地点只保留教学楼/教室级别。

### 标注格式

每条消息由 2 人独立标注，分歧由第 3 人裁决。标注为 JSON：

```json
{
  "id": "msg_001",
  "raw_text": "周四下午3点在A301开年级会，带学生证",
  "reference_date": "2026-10-17",
  "events": [
    {
      "title": "年级会",
      "type": "schedule",
      "date": "2026-10-22",
      "start_time": "15:00",
      "end_time": null,
      "location": "A301",
      "deadline": null,
      "preparation": ["学生证"],
      "needs_confirmation": ["end_time"]
    }
  ]
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `type` | `schedule`（要在某时参加）/ `ddl`（要在某时前完成）/ `task`（为前两者做准备） |
| `date` | 绝对日期，按 `reference_date` 推算 |
| `start_time` / `end_time` | 24 小时制；未知填 `null` |
| `location` | 原文中的地点；没有填 `null`，**不允许编造** |
| `deadline` | DDL 的截止时间；日程填 `null` |
| `preparation` | 需要携带/准备的东西，数组 |
| `needs_confirmation` | 模型自己认为不确定、需要用户确认的字段 |

## 3. 指标与通过标准

### 字段级指标

| 指标 | 定义 | 通过标准 |
|---|---|---|
| 事件召回率 | 标注重叠的事件中被识别出的比例 | ≥ 95% |
| 事件级完全正确率 | 一个事件的所有关键字段（标题/时间/地点/类型）都正确的比例 | **≥ 80%** |
| 时间准确率 | 日期 + 开始时间正确 | ≥ 90% |
| 地点准确率 | 地点非空时完全正确；标了无地点时模型也不编造 | **≥ 80%** |
| 类型准确率 | 日程 / DDL 判断正确 | ≥ 85% |
| 准备事项准确率 | 需要携带/准备的内容被抽出 | ≥ 80% |
| 幻觉率 | 原文没有的地点/时间/事件被编造的比例 | **< 5%** |
| 多事件召回率 | 一条消息含多个事件时，全部被找出的比例 | ≥ 80% |

### 体验与成本指标

| 指标 | 怎么测 | 目标 |
|---|---|---|
| 用户确认耗时 | 5 名用户对 10 条结果做确认/修改，计时 | 中位数 ≤ 10 秒/条 |
| 修改率 | 需要用户改动至少一个字段的比例 | ≤ 30% |
| 单条延迟 | 从转发到返回卡片 | P95 ≤ 5 秒 |
| 单条成本 | 模型 token + OCR 成本 | 首版 ≤ 0.05 元/条 |

**通过标准（写进 PRD 的硬门槛）：**

- 事件级完全正确率 ≥ 80%
- 地点准确率 ≥ 80%
- 幻觉率 < 5%
- 用户确认耗时中位数 ≤ 10 秒

任何一项不通过：地点准确率 < 80% → 地点降为二期；类型准确率 < 85% → 首版让用户手动选类型；幻觉率 ≥ 5% → 不允许自动写入，必须逐条确认。

## 4. 模型与 prompt 对比

至少比较 3 组：

| 组 | 模型 | prompt 策略 |
|---|---|---|
| A | 国内通用大模型 1（如通义千问） | zero-shot + JSON schema |
| B | 国内通用大模型 2（如 DeepSeek / GLM） | few-shot + JSON schema |
| C | 规则/正则 + 模型兜底 | 先用正则抓日期、时间、地点，模型只处理规则失败的部分 |

要求：

- 所有模型使用同一套 30 条标注数据；
- 固定 `temperature`（建议 0–0.2）；
- 输出必须是可解析 JSON，解析失败记为错误；
- 记录每条的消息 token、输出 token、耗时、成本；
- 不把 20 条留出集放进 prompt 示例。

### 推荐 prompt 结构

```text
你是校园通知信息抽取器。当前时间：{now}，当前学期第 {week} 周。
从用户转发的一条消息中抽取所有事件。规则：
1. 只抽取原文明确出现的信息，不允许推测地点、时间、人名。
2. 区分 schedule（要在某时参加）和 ddl（要在某时前完成）。
3. 相对时间按当前时间换算成绝对日期；不确定时填入 needs_confirmation。
4. 一条消息可能包含多个事件，分别输出。
5. 时间使用 24 小时制；无法确定结束时间填 null。
6. 只输出 JSON，不要解释。

输出 schema：
{ ... }

消息：
{message}
```

建议同时要求模型输出每个字段在原文中的 `span`（原文片段），便于人工复核和定位错误。

## 5. 错误分类

每条错误都打标签，最后看错误分布，不要只看总分：

- 相对日期算错（下周四 / 本周五 / 明天）
- 年份/学期跨年错误
- 节次换算错误（第 3-4 节 → 具体时间）
- 地点漏抽
- 地点抽错（把“带学生证”抽成地点）
- 地点编造
- 日程 / DDL 混淆
- 多事件合并成一个
- 同一事件重复输出
- 准备事项漏抽
- 输出 JSON 解析失败

错误分布决定下一步：如果主要是地点漏抽，优先补地点规则和 few-shot；如果是日期换算，优先把“当前日期/学期周次”注入 prompt 并加规则校验。

## 6. 用户确认测试

模型准确率只是上半场，用户愿不愿意改是下半场。

找 5 名目标用户，每人看 10 条识别结果：

1. 展示卡片：标题、时间、地点、类型、准备事项；
2. 让用户确认或修改；
3. 记录：确认耗时、改了哪些字段、有没有漏看错误；
4. 问一句：“如果它经常错在地点，你还会用吗？”

通过标准：

- 中位确认时间 ≤ 10 秒/条；
- 至少 4/5 的用户能在 10 秒内完成一条；
- 用户能指出被标红的“不确定字段”。

---

## 7. 课表导入测试（另开一轮）

### 样本

- Excel/CSV：3 份不同学校的真实课表
- 文字型 PDF：3 份
- 扫描型 PDF/图片：3 份
- 手机拍照：3 份（含倾斜、反光、截断）

### 指标

| 指标 | 通过标准 |
|---|---|
| 课程数量识别正确率 | ≥ 90% |
| 课程名/教师/地点字段准确率 | ≥ 80% |
| 星期、节次、周次（含单双周）准确率 | ≥ 80% |
| 从上传到可确认的耗时 | ≤ 30 秒 |
| 用户手动修改课程数 | ≤ 20% |

### 重点难点

- 第几节、起止周、单双周、合班课；
- 不同学校表格结构差异；
- 扫描件 OCR 噪声；
- 表头识别与字段映射；
- 导入后预览、逐条修改、批量删除。

---

## 8. 执行计划

| 阶段 | 时间 | 产出 |
|---|---|---|
| 收集并标注 30 条通知 | 2 天 | 标注集 v1 + 标注规范 |
| 跑 3 组模型/prompt | 2 天 | 原始输出 + 指标表 |
| 错误分析与 prompt 迭代 | 2 天 | 错误分类 + prompt v2 |
| 20 条留出集验收 | 1 天 | 验收报告 |
| 5 名用户确认测试 | 2 天 | 体验数据 |
| 课表导入测试 | 3–5 天 | 导入成功率报告 |

**结论输出格式（写进 `06-研究发现`）：**

```text
证据：30 条真实通知上，事件级完全正确率 83%，地点准确率 76%，幻觉率 3%。
结论：核心抽取成立，但地点未达到 80% 门槛。
产品影响：首版地点字段标为“需确认”，不自动写入；地点识别作为二期优化项。
```

---

## 9. 隐私与合规

- 收集真实通知前取得对方同意，说明用途；
- 标注前脱敏：姓名、学号、手机号、宿舍号、身份证号；
- 测试数据只用于本轮评估，不进入训练；
- 使用国内模型 API，确认供应商“不用于训练、不留存”条款；
- 测试结束后删除原始消息，只保留脱敏标注集与指标结果。
