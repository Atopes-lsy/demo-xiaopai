# 微信能力前置验证清单

## 为什么先做这个

产品形态定为「微信客服助手 + 微信小程序」后，核心入口“长按转发”依赖几条**尚未经过真机证实**的假设（见 `01-问题假设/prd前研究流程.md` 第 8 节）：

1. 转发单条消息，微信客服能收到完整内容；
2. 合并转发多条，微信客服能否解析出内容（官方已把 `merged_msg` 列为消息类型，但智能机器人场景实测取不到内容，微信客服是否一致未知）；
3. 与客服对话过之后，会话能在聊天列表里找回。

第 1 条决定“长按转发”这个核心入口能否成立；第 2 条决定多条录入的边界；第 3 条决定回访链路是否存在。**任何一条结果变化，PRD 都要改写**，所以在写 PRD 之前必须验完。

好消息是：**第一阶段不需要写代码，也不需要先搭回调服务器**。企业微信客户端本身就能看到客服收到的消息，验证成本约半小时。第二阶段（回调、订阅消息、小程序卡片、文件导入）需要最小 demo，见文末。

## 前置准备（一次性）

| 步骤 | 操作 | 备注 |
|---|---|---|
| 1 | 用公司执照注册企业微信 | **需要家人配合**——需法人身份验证或对公账户打款。这是唯一需要别人的一步，最可能卡住 |
| 2 | 管理后台 → 应用管理 → 微信客服 → 启用 | |
| 3 | 创建一个客服账号 | 接待方式**必须设成"仅人工"**，不要选"机器人+人工"，否则机器人会拦截或改写收到的消息 |
| 4 | 把接待人员设为自己 | |
| 5 | 复制客服链接或二维码 | |

准备完成后：手机微信扫码进入客服会话；企业微信（手机端或电脑端）即可看到用户发来的消息。

> 量级说明：企业微信未认证时，微信客服累计只能接待 100 位客户，认证后不限。自测用掉 1 个名额，**不必提前认证**。

## 验证一：转发单条文本（最关键）

**操作：** 用同学或自己的另一个微信号发一条消息，内容用真实场景，例如：

> 周四下午 3 点在 A301 开年级会，带学生证

然后**长按这条消息 → 转发 → 选择该客服会话**，到企业微信里查看收到什么。

| 观察到的结果 | 判定 | 后续动作 |
|---|---|---|
| 收到完整可读的文本 | ✅ 通过 | 核心入口成立，可写入 PRD |
| 收到"聊天记录"卡片、点不开、内容为空 | ❌ 不通过 | A 方案的核心入口不成立，需回到方案层重做 |
| 收到占位符或"暂不支持该类型" | ❌ 不通过 | 同上 |

**同时记录：** 收到的消息在企业微信侧显示为什么类型（文本/图片/其它），这决定后端拿到的是否是可解析的原始内容。**客户端能看到内容，不等于 API 报文里有内容**；消息类型和字段要等第二阶段用 `sync_msg` 抓包确认。

## 验证二：转发单条图片及其它类型

**操作：** 同样方式，分别转发一张通知截图、一个 PDF/Excel 文件、一条链接、一张小程序卡片、一个位置。

| 结果 | 判定 |
|---|---|
| 图片能正常查看 | ✅ 图片类通知可承接 |
| 显示“暂不支持” | ❌ 图片类通知不支持，产品文案需写明只识别文字；其它类型同理 |
| 文件可下载/可查看 | ✅ 可作为课表或附件导入的补充入口 |
| 小程序卡片能点开 | ✅ 可作为入口回流方式，但需另测身份绑定 |

## 验证三：合并转发能否解析

**操作：** 多选 2–10 条消息（文字、图片、文件、链接混合）→ 合并转发 → 选该客服会话。

| 结果 | 判定 |
|---|---|
| 能展开看到每条内容，且可逐条核对 | ✅ 可以放宽“只支持单条转发”的限制，合并转发可进入 MVP 设计 |
| 只看到一张打不开的卡片/占位 | 维持“单条转发 + 分次录入”，入口处讲清限制 |
| 能展开但缺少文件或部分类型 | 只对可解析类型开放合并转发，其余引导单条转发 |

> 注意：客户端能展开，只是“用户看得到”；还要在第二阶段确认 `sync_msg` 的 `merged_msg.item[]` 是否给出结构化内容、文件能否下载。两者都通过，才能写入 PRD。

## 验证四：会话能否找回（要隔天）

**操作：** 验证一做完后**隔一天**再打开微信，看聊天列表。

| 结果 | 判定 |
|---|---|
| 客服会话仍在列表，可直接继续对话 | ✅ 回访链路存在 |
| 会话消失，需重新扫码 | ❌ 回访**完全依赖小程序**，产品设计中的回访部分要重写 |

**这条最容易忘，且必须隔天。** 建议与验证一在同一天发起。

## 第二阶段：需要最小 demo 的能力验证

第一阶段的结论只回答“用户能不能把内容递进来、能不能找回来”。下面几项决定“递进来之后能不能稳定处理、能不能提醒”，需要最小 demo 或真机抓包。

| # | 验证项 | 怎么测 | 通过标准 | 优先级 |
|---|---|---|---|---|
| 5 | 回调链路与消息拉取 | 配置回调 URL/Token/EncodingAESKey；收到 `kf_msg_or_event` 后用 token + cursor 调 `sync_msg`；再调 `send_msg` 回复 | 文本/图片能落库；重复 `msgid` 不重复处理；cursor 持久化；模拟 5 秒超时和 3 次重试不丢消息 | P0 |
| 6 | 小程序卡片与身份打通 | 用 `send_msg` 发 `miniprogram` 卡；分别测 pagepath 加/不加 `.html`、同主体/非同主体 AppID；检查 `external_userid` 与 `unionid`/`openid` 的绑定 | 点击落到正确页面；能拿到可用于订阅消息的 `openid`；绑定失败有一次性 token 兜底 | P0 |
| 7 | 订阅消息 | 在目标类目后台查看可用模板；实测一次性/长期权限、单次 5 个、“总是保持”后的累积、关闭后的 43101、真实到达率 | 授权一次能发一条；额度账本准确；失败有站内兜底；不承诺长期自动提醒 | P0 |
| 8 | 文件导入 | `wx.chooseMessageFile` 从群聊/文件传输助手选真实 xlsx、pdf、jpg、png；测试 100 个上限、20MB 文件、文件名与解析；再测拍照 OCR | 课程数准确率 ≥90%、字段 ≥80%（见 `AI识别准确性测试方案.md` 第 7 节） | P0 |
| 9 | 端到端与限制 | 链接/QR 进入 → 删除会话后找回 → 用户发消息后 48 小时内发 5 条 → 隔 3 天再拉 `sync_msg`；iOS/Android 各测 | 会话可找回或明确只依赖小程序；5 条/48 小时限制有提示；3 天窗口外有补偿/兜底 | P1 |

> 微信客服 API 接管后，原生欢迎语、机器人、分流和人工分配会停用；这些都要自己实现，测试时不要依赖后台的“自动回复”。

## 执行顺序建议

1. **先跑验证一**——只需准备 + 一次转发，五分钟出结果，它是否通过决定后面还要不要做；
2. 同一天发起验证四（要隔天才有结论）；
3. 验证二、三顺带一起做；
4. 通过后再搭最小回调 demo，做第二阶段的 5–9 项；其中 5、6、7 是上线前 P0。

**最大的不确定在准备阶段**：注册企业微信需要家人配合，建议先把这一步约上。
