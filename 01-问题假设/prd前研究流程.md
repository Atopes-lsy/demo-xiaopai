# 课日程（转型前研究）：写 PRD 前的研究流程

> **2026-10-18 产品转型说明**：产品已更名为「小排」，核心改为「项目/消息 → 自动排期 → DDL → 今日待办」，课表不再是核心。本文的课表/通知假设保留作为转型前证据；新定位和假设见 [`08-PRD/PRD-v0.1.md`](../08-PRD/PRD-v0.1.md) 第 2.4、3 节。

## 0. 产品起点：个人真实经历

我长期使用学校课表小程序，并直接在课表中添加日程。频繁使用后发现三个问题：

1. **日程添加受限**：只能以固定上课时间段为单位添加，数量和时间粒度有限，无法灵活记录会议、汇报、志愿活动等事项。
2. **消息整理成本高**：微信群、QQ群中的通知通常包含时间、地点和活动等信息，但需要手动从长文字中提取，再填写到课表或日程中。
3. **DDL 与日程混在一起**：提交作业、报名、交材料等“必须在某个时间前完成”的事项，和会议、课程、答辩等“在某个时间参加”的事项没有明确区分。

这些是个人观察和初步假设，不能直接当作普遍用户结论。下一步要通过用户研究验证它们是否具有普遍性和足够频率。

## 1. 先定义研究问题

本项目需要回答：

- 多少学生使用课表工具同时管理日程？
- 用户是否需要在课表之外添加任意时间的活动？
- 用户从微信群、QQ群或其他渠道收到通知后如何整理？
- 用户最容易遗漏的是时间、地点、DDL还是准备事项？
- 用户是否需要把 DDL、日程和任务分开管理？
- 用户是否愿意主动复制、分享文字或图片给 App 识别？
- 用户能否接受识别后确认和修改？
- 用户是否愿意把课表和日程放在同一屏幕查看？

## 2. 写出待验证的假设

### 用户问题假设

- H1：固定课表时间段限制了学生添加非课程日程的灵活性。
- H2：学生经常从微信群、QQ群、教务系统或其他渠道收到需要记录的通知。
- H3：从长消息中手动提取时间、地点和活动信息是明显负担。
- H4：DDL 与日程混合展示会造成理解和管理混乱。
- H5：用户希望在查看课表时同时看到日程安排。

### 产品方案假设

- H6：支持从微信聊天记录直接选择文件（Excel、PDF、JPG/PNG）导入可以降低首次建立课表的成本。
- H7：用户长按单条消息转发给微信客服助手后，自动提取活动、时间和地点，可以减少手动录入。
- H8：将内容区分为日程、DDL 和任务，并使用不同视觉呈现，可以提高理解效率。
- H9：用户愿意在自动识别后确认或修改，而不是要求系统无确认直接写入。
- H10：用户愿意为了识别群通知而额外使用一个微信客服助手，而不只是用小程序本身。

## 3. 研究个人当前使用流程

先把自己的真实流程写清楚，作为后续访谈和原型的基础：

```text
收到课程或活动消息
→ 打开学校课表小程序
→ 找到添加日程入口
→ 按固定时间段填写
→ 手动提取时间、地点和活动
→ 保存
→ 在课表中查看
```

记录每一步：

- 使用了什么入口 微信下拉小程序
- 花了多长时间 极快
- 哪一步最容易出错 有多个日程挤在同一个时间段，不能直观区分先后
- 哪些信息无法填写 时间地点做什么要手动输入，并且每个学期课表更新后，以前手动输入的模块残留，要手动删除，很不方便。
- 日程和 DDL 如何被区分 小程序中无法被区分。（我认为可以：日程只出现在当前时间块，ddl要从现在用颜色条等区分方式持续到结束时间。

研究结论不能只写“竞品没有这个功能”，还要说明：

## 5. 做用户访谈

先访谈 8–12 名大学生，优先找：

- 使用学校课表小程序的人
- 经常使用微信群或QQ群的人
- 有课程、社团、志愿或小组汇报安排的人
- 遇到过漏交作业或错过活动的人

访谈重点：

- 最近一次添加非课程日程是什么？
- 课表小程序的固定时间段是否限制过你？
- 最近一次从群消息中整理时间、地点和活动是什么？
- 你当时如何处理？花了多久？
- 是否发生过漏记、错记或找不到信息？
- 你如何区分日程、DDL 和准备任务？
- 你是否希望课表和日程同屏？
- 你是否愿意主动分享或复制消息给 App？
- 对上传聊天内容最担心什么？

访谈原则：

- 先问过去真实发生的事情，再问未来需求。
- 不先介绍方案，避免用户迎合。
- 要求用户讲具体最近一次经历。
- 记录原话和行为，不只记录主观看法。

## 6. 再做问卷

问卷用于验证频率和比例，建议收集 50–100 份有效样本。

验证内容：

- 使用课表小程序的比例
- 添加非课程日程的频率
- 从群消息整理事项的频率
- 最容易遗漏的信息类型
- 用户是否区分 DDL 和日程
- 当前使用的工具
- 对课表与日程同屏的需求
- 对主动分享文字、图片识别的接受程度
- 用户愿意接受的确认时间

问卷结果只能说明样本中的趋势，不能直接代表全部大学生。

## 7. 设计概念测试

在完成访谈和问卷后，再向用户展示以下产品概念：

> 一个微信小程序，把课程和灵活日程放在同一屏幕，另配一个微信客服助手承接消息。课表可以通过从聊天记录里直接选文件（Excel、PDF、JPG/PNG）导入；群里的通知则长按单条消息，转发给客服助手，由它识别后回一张小程序卡片，点开即可确认。提交作业、报名、交材料等 DDL 与会议、答辩、活动等日程分开呈现，并可关联准备任务。

测试以下内容：

- 用户是否理解产品价值
- 用户最想使用哪个入口
- “课表、日程、DDL、任务”的区分是否清楚
- 用户是否接受识别后确认
- 用户最担心哪种识别错误
- 用户是否愿意持续使用，而不只是开学时使用

## 8. 技术可行性调研

> 详细技术路线、架构、课表导入与风险见 `05-技术与合规调研/技术可行性调研.md`；AI 抽取的指标与测试方法见 `05-技术与合规调研/AI识别准确性测试方案.md`。

技术名称先作为待验证项，不要在 PRD 中直接写成已确定方案。产品形态已从 Android 应用改为“微信客服助手 + 微信小程序”，本节按新形态重写。

### 微信生态能力边界（本次新增）

“长按转发”是这个产品的核心入口，但它在微信里不是自由可用的能力，边界必须先划清楚：

- **单条消息转发：推断可行，待真机验证。** 用户长按单条消息转发时，官方没有专用消息类型或说明；可能按原类型到达，也可能以卡片/占位形式出现。微信客服 API 可接收文字、图片、语音、视频、文件、位置、链接、名片、小程序、菜单、事件和 `merged_msg`，但“接口支持该类型”不等于“转发后能收到完整内容”。属推断，必须真机抓 `sync_msg` 验证。
- **合并转发（多选多条）：不能按“不可用”定稿。** 企业微信开发者社区有实测反馈：向智能机器人合并转发聊天记录，回调只收到一个标识，报文中不含内容，也没有可拉取内容的 media_id；要取内容需走会话内容存档，按席位收费。但智能机器人和微信客服是不同接口；微信客服 API 官方文档已把 `merged_msg` 列为消息类型，含 title、item[]，item 为嵌套普通消息，支持范围未穷举。状态：官证存在 + 待测内容。
- **助手入口：没有自然发现路径。** 用户不需要加好友、不需要关注，但也没有“搜到”的途径，必须有人把客服链接或二维码递到用户面前。公众号菜单、小程序内客服按钮、搜一搜品牌官方区这些常规挂载位对新项目全部不可用，冷启动只能靠同学转发、班级群发二维码、海报。另有接待量约束：企业微信未认证时累计只能接待 100 位客户，认证后不限，测试阶段不必认证。待验证：用户与客服对话过一次后，该会话是否保留在聊天列表、下次能否自行找回。

产品影响：**在真机结果出来之前，不把“只能单条转发”写进产品承诺。** 测试结果分三种：`merged_msg` 可解析 → 允许用户多选合并转发；只能拿到卡片/占位 → 只承诺单条转发，入口处讲清，多条时引导分次转发；单条也失败 → 核心入口改为“复制/粘贴 → 小程序”兜底。

连带结论：如果合并转发不可用，“从一条消息中抽出多个对象”就是多条目录入的唯一路径，权重从锦上添花变成核心能力；如果可用，则作为效率增强，不替代单条入口。

### 课表导入

验证：

- 从微信聊天记录选择文件（Excel、PDF、JPG/PNG）：小程序可从聊天中直接选文件，用户收到课表的位置与导入位置在同一处，路径短于原先的“文件管理器找文件”
- 拍照或从相册选择图片
- Excel/CSV：表格解析、字段映射和周次识别
- PDF：文字型 PDF 提取，扫描型 PDF 的 OCR
- JPG/PNG：OCR、表格结构识别和课程字段提取
- 中国高校常见格式：第几节、起止周、单双周、合班课
- 教务系统对接：需服务端代爬；小程序内嵌网页受业务域名限制，不能直接打开各校教务系统

候选技术方向：

- 结构化文件解析库
- OCR
- 表格识别
- 规则解析
- 大模型结构化提取

解析放服务端，不放进小程序包：主包体积有上限，表格解析和 OCR 依赖的库体积大，且模型调用本来就在服务端。

### 聊天内容提取

验证：

- 微信客服回调链路：配置回调地址、验签、拉取消息内容、回复小程序卡片
- 回调只推送 `kf_msg_or_event` 事件和临时 token，正文必须用 token + cursor 调 `sync_msg` 拉取；`sync_msg` 只保留最近 3 天，回调 5 秒超时重试 3 次，必须立即落库、按 `msgid` 幂等、持久化 cursor 并定时补偿
- API 接管后原生欢迎语/机器人/分流停用；用户主动发消息后 48 小时内最多发 5 条，用户再发才续额度
- 客服侧只有 `external_userid`；需通过同主体绑定小程序/开放平台或卡片一次性 token，才能关联到小程序 `openid`，否则订阅提醒无法触达
- 兜底入口：用户复制消息后在小程序内点击触发读取剪贴板（小程序不能后台监听剪贴板，必须由用户动作触发）
- 中文日期、时间、地点、相对日期识别
- 从一条消息中拆分多个活动（若合并转发不可用，这是多条录入的唯一路径；合并转发能否解析待真机验证）
- “课前”“明天下午”等模糊时间的确认机制

候选技术方向：

- 正则和规则解析
- 中文 NLP 实体识别
- 大模型 JSON 结构化输出
- 规则校验与置信度判断

### 订阅消息的额度约束

小程序订阅消息中，教育类目下“在线教育”通常只能使用一次性订阅：用户每授权一次下发一条消息。官方当前单次调用最多请求 **5 个模板**（旧文档多为 3 个）；长期订阅仅向政务民生、医疗、交通、金融、教育等**线下公共服务**类目开放，且模板库必须有对应模板。在线教育未被明确列入，但官方也未明文规定“只能一次性”；项目按最保守的一次性订阅设计，实际可用模板以目标类目后台为准。

机制细节（易被误解，PRD 中要写准）：用户可勾选“总是保持以上选择，不再询问”，此后调用授权接口不再弹窗，但**每次仍需用户主动点击**才算攒下一次额度；额度可累加，永久有效直到用完，或被用户在设置中关闭订阅时清零。

由此确定的边界：

- 不能对外承诺“设一次 DDL，到期自动提醒”这类长期提醒能力
- 真正的摩擦点不是“反复弹窗”（勾选保持后不再弹窗），而是**额度是消耗品，且只能靠用户主动点击来补**
- 产品上设计成“每次进入小程序时顺手补充额度”，并替用户决定把有限的额度花在哪几件事上
- 额度耗尽时的兜底是打开小程序看到的“本周 DDL”栏，而不是推送

这条约束会直接影响产品文案的措辞，PRD 中必须写明，不得夸大提醒能力。

### 信息分类

验证如何区分：

- 日程：需要在某个时间参加或发生
- DDL：必须在某个时间前完成或提交
- 任务：为了日程或 DDL 需要准备的行动

推荐采用“规则 + NLP/大模型 + 用户确认”，而不是让模型无确认写入。

## 9. 隐私与合规边界

原方案基于 Android 本地应用，边界相对简单。改为微信客服 + 小程序后，用户主动转发的通知内容会经过服务器，合规要求提高一档，边界需要重写。

第一版产品边界：

- 不读取微信或 QQ 历史聊天，不申请任何聊天记录读取权限
- 不后台监听剪贴板；小程序读取剪贴板必须由用户点击触发
- 只处理用户主动转发、复制或选择上传的内容
- 转发的消息会到达服务器用于识别，这一点要在入口引导处明示，不能默认用户知道
- 默认不保存原始聊天全文：识别完成后只保留结构化结果，原文在用户确认后删除
- 只保存用户确认后的结构化日程、DDL 和任务
- 课表文件同样上传服务端解析，需说明留存策略
- 提供删除识别记录和账户数据的入口
- 按个人信息保护相关要求准备隐私政策与告知同意流程，这是上架审核的前置项

待确认项：微信客服会话的数据留存规则；是否需要单独的用户协议。

**2026-10-17 补充：** 合规清单、P0 动作、数据留存建议、需律师确认的问题已整理到 `05-技术与合规调研/合规与隐私调研.md`。最优先的五件事：

1. 隐私政策 + 微信《用户隐私保护指引》+ 首次单独同意弹窗；
2. 完成个人信息保护影响评估（PIA），尤其是第三方 LLM/OCR 委托处理；
3. 小程序 APP 备案 + 后端域名 ICP 备案；
4. 与 LLM/OCR/云供应商签数据处理协议，确认境内存储、不训练、不留存；
5. AI 结果标“AI 整理，请核对”，聊天原文解析后即删。

## 10. 整理研究发现

每条发现使用“证据 + 结论 + 产品影响”：

```text
证据：10名受访者中有7人每周至少一次从群消息整理时间或地点。
结论：消息整理是高频问题。
产品影响：MVP优先支持长按转发单条消息和点击触发剪贴板识别。
```

```text
证据：多数用户愿意主动分享文字，但不接受后台读取聊天。
结论：隐私边界必须是用户主动触发。
产品影响：采用“长按转发给微信客服”和“点击触发读取剪贴板”，不申请聊天记录读取权限。
```

```text
证据：用户把交作业和参加答辩视为不同类型的事情。
结论：DDL 与日程需要独立展示。
产品影响：首页分区展示，并支持从日程生成准备任务。
```

## 11. 确定 MVP

### 必做

1. 课表导入：从微信聊天记录选择文件（Excel、PDF、JPG/PNG），以及拍照识别
2. 长按转发单条消息给微信客服助手
3. 提取活动、日期、时间、地点、DDL 和任务
4. 识别结果确认、编辑和取消
5. 课表与日程同屏查看
6. DDL、日程、任务的不同视觉呈现
7. 小程序内日程、DDL 和任务列表
8. 订阅消息提醒（受额度约束，见第 8 节）
9. 用户反馈和错误记录

### 暂不做

- 合并转发多条消息（待真机验证；结果出来前不进入 MVP 范围，见第 8 节）
- 自动读取微信或 QQ 历史消息
- 后台监听剪贴板
- 独立 App、iOS、Android 原生
- 海外市场和多语言
- 社交与多人共享
- 复杂教务系统登录
- 自动发送或修改聊天消息

## 13. PRD 后验证

在进入开发前，有几项前置验证必须先做完。操作步骤、通过标准和结果记录表见 `05-技术与合规调研/微信能力前置验证清单.md`，全部无需写代码：

**验证一：转发能力。** 用一台真实设备，在微信里长按一条消息转发给微信客服会话，确认后端能收到完整内容。单条转发的可行性目前只是推断（见第 8 节），这条不通过，“长按转发”这个核心入口就不能写进 PRD。

**验证二：会话能否找回。** 用同一台设备隔一天再打开微信，看与客服的会话是否还在聊天列表里、能否自行继续对话。这决定回访链路是否存在（见第 8 节）。若找不到，产品的复访只能完全依赖小程序入口。

**验证三：合并转发能否解析出内容。** 在真机上多选 2–10 条消息（含文件/图片/链接）合并转发，确认官方 `merged_msg` 在微信客服场景下到底给不给 item 内容。能解析就放宽入口限制；只能拿到卡片/占位，就维持“单条转发 + 分次录入”；如果连单条都失败，回到“复制/粘贴 → 小程序”兜底。

```text
研究 → PRD → Figma低保真 → 可点击原型 → 5名用户测试 → 修改PRD → 开发小程序 MVP
```

核心指标：

- 课表导入成功率
- 聊天内容识别成功率
- 时间、地点识别准确率
- DDL/日程分类准确率
- 用户修改率
- 确认保存率
- 从转发到保存完成的时间
- 7日留存
