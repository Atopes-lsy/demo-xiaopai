# v3.3：E1b-1 max_tokens 参数实验

> 迭代顺序：v3.0 基线（`v3/` 根目录）→ [v3.1](../v3.1/README.md) → [v3.2](../v3.2/README.md) → **v3.3（本目录）**。
>
> 状态：**已执行，未采用；操纵检查失败（2026-10-19）**。在火山方舟直连、temperature `0.1`、抽取 LLM 单次调用口径下，把 `max_tokens` 从 `2000` 改为 `1200`：变量组 **19/21** 次 `completion_tokens > 1200`（最大 2909，`finish_reason` 全为 `stop`）；控制组也有 **4/21** 次 `> 2000`（最大 3085）。两组输出都超过各自设定上限，说明该参数在这个请求配置下没有实际约束生成。因此**不能把两组的质量或延迟差异归因于 max_tokens**，也没有获得“该参数无效”的模型层结论；只能写“本次设置未生效”。产品决定维持 `2000`，但这不等于验证了 2000 是更优值。

## 1. 实验问题与条件

| 项目 | 值 |
|---|---|
| 唯一变量 | `max_tokens`：控制组 C `2000` / 变量组 V1 `1200` |
| Prompt | v3-opt + E0.1 deadline 补丁，全文一致 |
| 模型 | `doubao-seed-2-0-pro-260215`，非推理，thinking disabled |
| temperature | `0.1`（两组一致） |
| JSON 模式 | 开启（`response_format: json_object`） |
| 测试集 | id 2–8，共 7 条脱敏通知 |
| 测试基准日 | `2026-10-18 09:00 星期日`，`Asia/Shanghai` |
| 运行方式 | 每条 3 次，串行；每组 7×3 = 21 次 |
| 渠道 | 火山方舟直连（不是 Coze 主图托管） |
| 延迟口径 | `latency_scope=extract_llm_e2e`：只包抽取 LLM 一次调用，不含意图、normalize、平台排队 |
| 输入 | 42/42 次 `input_present=1` |

> **口径边界**：本次既不是 Coze 主图（当前主图抽取 temperature 为 `0.0`），也不是完整工作流。不能与 7×1 主回归的全流程 median 11040 ms、v3 的 21 次抽取节点 median 27202 ms 横比，也不能把结论直接套到 Coze 主图生产配置。

数据文件：

- [e1b1_variant_max1200.csv](e1b1_variant_max1200.csv)：变量组 21 行
- 两份 CSV 均含 `latency_ms`、`latency_scope`、`finish_reason`、`prompt_tokens`、`completion_tokens`、`output_chars`、`events_cnt`、完整 `predicted_events` 和 `notes/error`。

## 2. 操纵检查：先看参数有没有生效

| 组别 | 设定 max_tokens | 实际超过设定值 | 最大 completion_tokens | finish_reason |
|---|---:|---:|---:|---|
| C | 2000 | **4/21** | **3085** | 21/21 `stop` |
| V1 | 1200 | **19/21** | **2909** | 21/21 `stop` |

> 计数口径：直接使用 CSV 的 `completion_tokens`，条件为严格大于设定值。用户汇报“V1 18/21 次 >1200”；逐行复核为 **19/21**（只有 id 6 run3 的 987 和 id 7 run1 的 247 不超过 1200）。该 1 条差异不改变“参数未生效”的结论。

`max_tokens` 是生成上限，不是目标长度。如果上限实际生效，超过上限的输出应被截断，`finish_reason` 不应仍为 `stop`。本次两组都有超过各自上限的输出且全部正常结束，说明：

1. `1200` 没有绑定到实际请求，或被网关/调用层忽略；
2. 连控制组的 `2000` 也没有表现出上限约束；
3. C 和 V1 在这些运行里**很可能实际是同一有效配置**，两组差异只能当重复运行噪声，不能做因果解释。

**结论怎么写**：写“本次 max_tokens 设置未生效，实验不能检验该参数的效果”。不要写“max_tokens 参数无效”，因为模型在真正受限时是否变快/变差，本次没有回答。以后若还要测试，先做一次小上限冒烟（例如 `max_tokens=300`），确认出现截断或 `finish_reason=length` 后再跑 21 次；没有通过冒烟就不进入正式实验。

## 3. 延迟

| 分组 | n | 平均 (ms) | 中位 (ms) | p95 (ms) | 最小 (ms) | 最大 (ms) |
|---|---:|---:|---:|---:|---:|---:|
| C 全部运行 | 21 | 37911.7 | 34947 | 66866 | 8920 | 69690 |
| V1 全部运行 | 21 | 35861.9 | 36278 | 46386 | 7853 | 59747 |
| C 非空输出 | 18 | 42141.1 | 36198 | — | 26731 | 69690 |
| V1 非空输出 | 20 | 37262.3 | 36418.5 | — | 22603 | 59747 |

> p95 按最近秩（21 个样本取排序后的第 20 个值）；非空组只有 18/20 个样本，不单独报 p95。

- 全部运行的中位数 C 34947 vs V1 36278 ms，V1 反而慢约 1.3 s；非空输出中位数 36198 vs 36418.5 ms，差约 0.2 s。**没有中位数层面的收益。**
- C 的平均值和 p95 被少数长尾拉高（最大 69690 ms）；V1 的 p95 较低，但 21 个样本的 p95 不稳定，且操纵已失败，不能写成“V1 降低尾延迟”。
- 空输出运行本身更快（C 8.9–16.3 s，V1 7.9 s），会拉低“全部运行”的统计；但不能把“更快”与“质量更差”混在一起解释。
- 因为 max_tokens 未生效，以上延迟差异不构成任何参数结论。

## 4. 质量

### 4.1 主事项是否抽出

| 组别 | 主事项命中 | 失败运行 |
|---|---:|---|
| C | 18/21 | id 2 run1、id 7 run2、id 7 run3 |
| V1 | 20/21 | id 7 run1 |

失败明细：

| 组别 | id/run | completion_tokens | latency_ms | notes |
|---|---|---:|---:|---|
| C | id 2 run1 | 519 | 16275 | 无可记录事项 |
| C | id 7 run2 | 408 | 12411 | 未提供待抽取的通知原文，无可记录事项；但该次 `input_present=1` |
| C | id 7 run3 | 297 | 8920 | 无可记录事项 |
| V1 | id 7 run1 | 247 | 7853 | 无可记录事项 |

- C 的 id 7 run2 是模型声称“没有收到原文”，但记录显示输入存在。这是一次**模型输出异常/输入回执问题**，不能写成“输入缺失”，也不能只靠 `events_cnt` 判断。该现象仍需单独排查。
- id 7 共 6 次（C 3 次 + V1 3 次）只有 3 次抽出：C 1/3、V1 2/3。id 8 两组均 3/3，deadline 为 `2026-08-11 23:59`，priority 为 `null`。
- id 2：C 1/3、V1 3/3。
- 主事项命中只表示“主事项存在”；本次没有对时间、地点、类型、优先级做完整逐项落表评分。不要把 20/21 或 18/21 写成“全部字段准确率”。

### 4.2 多抽口径

用户按“主事项 + 最多 1 条隐含 task”口径记 `over_split=0`。但从原始 `events_cnt` 看：

- C：1 事件 15 次，2 事件 3 次（id 2 run2/3、id 7 run1）；
- V1：1 事件 15 次，2 事件 5 次（id 2 ×3、id 7 ×2）。

这些 2 事件运行都包含 1 条隐含准备 task。按当前 Prompt 规则（隐含 task 最多 1 条）可以不算多抽；如果改用“每条输入必须恰好 1 个事件”的严格口径，结果会不同。以后评分表必须写明采用哪个口径，不能只写“多抽=0”而不说明规则。

### 4.3 其他观察

- **id 4 周次歧义**：C 3/3、V1 3/3，6 次都同时写了 `2026-10-22` 与 `2026-10-29`，并说明按 10/22 解析。这与 7×1 主回归（Coze 托管、temp 0.0）里 id 4 未写周次歧义相反。它是温度假设的**反向证据**：temp 0.1 直连并非整体更差，渠道、Prompt 状态、输入和采样都可能影响结果，不能只归因温度。
- **负例检查**：V1 的 N1–N4 各 1 次，0/4 deadline 误抽（用户反馈）；**控制组负例没有运行**。因此只能说“变量组负例未新增误抽”，不能说“两组负例都零误抽”；同渠道负例证据只有一侧。
- 本次变量组的负例不能补偿控制组质量门：控制组 id 7 仅 1/3，本身没有达到工单要求的 3/3。

## 5. 解释与决定

1. **E1b-1 不是一次有效的 max_tokens 实验。** 参数没有绑定，C/V1 有效配置很可能相同；质量 20/21 vs 18/21 属于重复运行噪声，不能写 V1 更好，也不能写 max_tokens 影响质量。
2. **维持 `max_tokens=2000`。** 这是“不做无依据的配置变更”，不是因为实验证明 2000 最优。生产配置没有因本次实验被改动，不需要“回退”操作。
3. **不要再跑 800/1200**，直到确认参数实际传入请求并能制造截断；否则只是重复本实验。也不要用本次数据支持“参数无用”或“短输出更快”的结论。
4. **id 7 在直连 temp 0.1 下 3/6 命中，值得继续观察。** 但主图 temp 0.0 的 E0.1 id7 是 3/3、7×1 主回归 id7 是 1/1；两组样本、渠道、Prompt 运行状态不同，不能直接说“温度 0.1 导致漏抽”。id 4 的 6/6 歧义正确是明确的反向信号。
5. **本次没有证明 E1b-1 的任何采用条件。** 控制组 id7 未达 3/3、负例只跑了一侧、操纵失败，三项都不满足。结果文件保留，不删除。

## 6. 后续温度实验（建议，未执行）

若要验证温度与 id 7/id 2 偶发漏抽的关系，需要同渠道、同 Prompt、同输入、同测量点的受控实验：

- 变量：抽取 temperature `0.0` vs `0.1`，其他全部固定；先确认主图/脚本实际使用同一渠道。
- 规模：先做 7 条 × 3 次 × 2 组；如果 id 7/id 2 仍有漏抽，再对这两个 id 各追加 7–10 次/组做定向观察。
- 指标：主事项命中、空输出率、id 7 deadline 命中、id 2 命中、id 4 ambiguity、输出 token 和延迟。
- 记录：逐次保存完整输入、完整输出和 `input_present`；区分“模型说没收到原文”与真正输入缺失。
- 判定：只做方向性判断，不写统计显著；生产 temperature 在看到完整结果前不改。

该实验尚未执行，不能把本文件中的观察写成温度结论。

## 7. 边界

- 7 条样本 × 3 次，只作方向性观察，不做统计外推。
- 本次是火山方舟直连、temp 0.1、抽取 LLM 单次调用，不是 Coze 主图 temp 0.0，也不是端到端。
- 质量评分以“主事项是否抽出”为主；完整字段级评分未单独落表。
- max_tokens 未生效是**操纵失败**，不是“参数无效果”的干净结论。
- 负例只有 V1 一侧；控制组未做负例检查。
- 原始数据中的 `notes` 可能是模型自称“未收到原文”，不能直接当输入缺失证据；以 `input_present` 和完整输入记录为准。
