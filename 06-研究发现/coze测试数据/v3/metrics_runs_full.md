## 主要问题

1. **输入缺失（3 次，最优先）**：id 2 run1、id 6 run2、id 7 run3 的 `notes` 明确写“未提供待抽取的原文内容/目标原文内容”。这更像工作流变量未传入或传空，不是模型抽取能力问题。它会让用户在真实使用中看到“没有事项”的错误结果，优先级高于 prompt 微调。
2. **多抽（2 次）**：
   - id 2 run2 输出 5 个事件：1 个检查 + 4 个 task。expected 备注允许 1 个有原文依据的隐含准备 task，但不允许拆成多个；4 个 task 还都给了无原文依据的 P1。
   - id 7 run1 输出 2 个事件：deadline + “打磨参赛作品” task；task 被给了与提交相同的截止时间，且没有标成“建议”。expected 备注允许隐含 task，但要求标明建议、不得给新的硬截止。
3. **周次歧义仍未说明（id 4×3）**：三次都输出 10/22 15:20，但 `ambiguity` 只写“原文未写上午/下午”，没有写“下周四可能是 10/22 或 10/29”。时间值对，不代表歧义处理完整。
4. **优先级过度推断**：id 2 run2/run3 的 task 给了 P1，原文没有依据。P1 虽然不是 P3，但仍应在没有截止时间时回到 `null`，或在 `notes` 里明确标成建议。
5. **空返回原因未确认（id 7 run2）**：只写“无可记录事项”，无法判断是输入缺失还是模型漏抽；应结合运行日志核对。

## 对下一轮的要求

- 先在脚本/工作流里加输入校验：`raw_text` 为空时直接返回输入错误，不能进入抽取，也不能输出“无可记录事项”。
- 给 `predicted_events` 加“隐含 task 最多 1 条”的约束；隐含 task 的 `priority` 和 `deadline` 默认 `null`，除非原文对这条 task 明确给出了优先级或截止。
- 保留 `ambiguity` 的周次检查：`下周四` 这类相对时间必须写出候选日期。
- 重新跑 3 轮时，每次都保存完整输出和输入变量；不要只保存 `events_cnt`。
- 这组 21 次运行的质量结果可以写进简历/面试，但必须写成“21 次完整重跑中 15/21 端到端通过、15/17 非空事件级通过”，不能写成“3 轮质量稳定 7/7”。
