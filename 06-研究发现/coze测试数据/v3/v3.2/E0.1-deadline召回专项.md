## 0. 初始判断（已由探针验证）

> 后续（2026-10-19）：探针确认这是通用偶发漏抽（P8 1/3、P6 2/3），不是 id 7 个例；本节保留为当时的判断记录，结果见 5.1。

用户判断：

- id 7 漏抽不是基础链路故障，而是 v3-opt 的“信息日期 / 名单公布不抽”规则在 deadline 型公告上被整段误用；
- 主图当前 v3 配置在 id 7 上能命中，recheck 兜底没有被触发；
- 因此 v3 反而是健康配置。

这个机制判断**有可能是对的**，但版本归因目前证据不足，先记为高优先级假设，不写成定论：

1. **这条规则不是 v3-opt 新增的。** v3 的六.3 和自检 3 与 v3-opt 逐字相同；“名单公布/结果公布等信息日期不抽，只写 notes”最早在 v2 就有。v3-opt 新增的是输入校验、多抽上限、周次歧义，Prompt 从 7288 字符增加到 8169 字符。更准确的说法是：**既有规则在更长的 Prompt 里被过度执行，或运行波动**，不能直接写“v3-opt 强化了这条规则”。
2. **v3 在 id 7 上也不是稳定 3/3。** 补充 B 的 21 次里，id 7 是 run1 多抽、run2 空返回、run3 输入缺失；初测 7/7 和补充 A 的 run2 命中只能证明“某次命中”，不能证明主图 v3 稳定健康。若主图 v3 的 id 7 是 3/3，需要把 3 次的完整输出和意图结果保存下来，才能升级为结论。
3. **recheck 没触发是正常的。** recheck 只在“空输出 + 截止线索命中”时触发；v3 命中时本来就不该触发。它不能用来证明 v3 健康，也不能证明 v3-opt 不需要兜底。
4. **“稳定判空”和“偶发整段误判”是两种不同结论。** 前者需要 0/3 或接近 0/3 的证据；后者需要 1/3、2/3 的逐次计数。现在不能同时使用这两个说法。

**最小验证**：同一模型、同一参数、同一基准日、同一输入绑定，跑两组：

- A：主图 v3 × id 7 × 3 次；
- B：v3-opt × id 7 × 3 次。

记录 `intent_raw`、`has_recordable_event`、完整 `events`、`notes`。只有 A 稳定 3/3、B 稳定漏抽，才能把“v3-opt 导致”写成因果；如果两边都偶发，问题在规则本身或采样波动，不是 v3-opt 独有。

**修复方向**：不建议回退到 v3。v3-opt 已解决输入缺失和多抽，并增加了 id 4 周次歧义自检；但 E0.1 后的 7×1 主回归仍没写出 10/22 vs 10/29，所以只能写“已加自检、未验证修复”，不能写“已解决”。回退会把输入缺失和多抽带回来。更小的改法是保留 v3-opt，只改写信息日期规则：

> 名单公布/结果公布等信息日期不抽；但同一段出现提交/报名/缴费/订购截止时，该截止必须单独抽 deadline，不能因为整条像公告就判空。

这样既保留三项前置修复，也只改一个语义变量。

## 3. Prompt 补丁（已验证，已并入主图配置）

把下面规则追加到 v3-opt 抽取 Prompt 的“不要抽取的内容”之后，或并入类型定义/自检；**一次只加这一组规则**，不要同时改模型、参数和 schema。

```text
【deadline 召回补充规则】
1. 公告/通知里出现“提交 / 报名 / 缴费 / 订购 / 申请 / 注册”等用户动作，并给出“截止 / 前完成 / 窗口 / 之内”等时间边界时，必须抽成 deadline；即使整条文本看起来像通知、公告，或没有“请 / 需要 / 记得”等主语，也要抽。
2. “名单公布 / 结果公布 / 活动开始 / 晋级名单”等信息日期仍然只写 notes；但如果同一句还明确写了用户的提交/报名截止，提交/报名截止必须单独抽 deadline，不能因为同段有信息日期就整条判空。
3. 倒计时与明确截止日期不一致时，以明确日期为准，仍要抽 deadline，并在 ambiguity 说明；不得因为矛盾判空。
4. 截止日期已过期不等于不可记录：仍按原文输出 deadline，priority 用 null，并在 notes 或 ambiguity 标注“已过期”。
```

补丁的设计意图：
- 第 1 条解决“公告型 + 无主语”导致的漏抽；
- 第 2 条把“信息日期”和“用户截止”切开，避免六.3 被过度应用；
- 第 3 条解决 id 7 的“倒计时 3 天 vs 10/20”；
- 第 4 条解决 id 8 的“已过期”被丢弃。

## 4. recover 兜底：先确定性触发，再考虑第二次 LLM

### 4.1 触发条件

`deadline_guard` 代码节点（本地实现见 [deadline_guard.js](deadline_guard.js)，本地测试见 [deadline_guard.test.js](deadline_guard.test.js)，15/15 通过）只做触发判断，不抽日期：

- 命中“动作 + 时间边界”：如“提交截止”“报名截止”“缴费截止”“订购窗口”“申请截止”“前完成提交”“内完成预订”；
- 同一条文本里还要有日期/时间表达：`10月20日`、`10/20`、`2026-10-20`、`本周五`、`下周三`、`月底`、`倒计时3天` 等；
- 只出现“名单公布 / 结果公布 / 活动开始 / 晋级名单”时不触发；
- 只有“截止”但没有日期、或只有日期但没有用户动作时不触发。

输出：

```json
{
  "deadline_cue": true,
  "info_date_only": false,
  "force_extract": true,
  "evidence": "提交截止：10月20日 23:59",
  "reason": "action_deadline_with_date"
}
```

### 4.2 接法

```text
validate_input
  → deadline_guard
      → 意图判断 LLM
          ├─ has_recordable_event = false 且 deadline_guard.deadline_cue = true
          │     → 强制进入抽取（零额外 LLM 调用）
          └─ has_recordable_event = true
                → 抽取 LLM
                    → normalize_extraction
                        → 条件：events_cnt = 0 且 deadline_guard.deadline_cue = true
                            ├─ 是 → recover LLM（只抽 deadline，短 Prompt，max_tokens 300–500）
                            └─ 否 → 结束
```

- `events_cnt` 需要在 `normalize_extraction` 返回里增加一个 **输出字段**（不是改 `result_json` 的 schema）：`events_cnt: events.length`。这是加法，不改变下游 JSON 语义。
- recover LLM 的输出必须走同一个 `normalize_extraction`，不能直接把模型文本拼进结果。
- recover 只允许补充 `type=deadline` 的事件；不能新增 event/task，不能把信息日期转成 deadline。
- 合并时按 `title + deadline` 去重；如果主抽取已有 deadline，不重复添加。

### 4.3 如果暂时不加第二次 LLM

至少把“空输出”改成显式待确认：

```json
{
  "events": [],
  "needs_confirmation": true,
  "notes": "检测到截止信息但未抽取，请确认"
}
```

这不会恢复事件，但能避免用户看到“无可记录事项”的错误结论。它比静默失败好，但不能算解决召回问题。
