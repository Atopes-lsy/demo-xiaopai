### E0.1：deadline 召回专项（已闭环 2026-10-19）

**结果（用户反馈 2026-10-19）**：探针确认 v3-opt 存在通用偶发漏抽（P8 1/3、P6 2/3）；应用 Prompt 补丁后 P1–P8 正例均 ≥2/3（P3 2/3，其余 3/3；P1 run1 为 JSON 损坏、raw 含正确事件），负例 0/12 误抽。补丁已并入主图配置；id 7 3/3（`2026-10-20 23:59`，P1）、id 8 3/3（`2026-08-11 23:59`，priority `null`，已过期），`test_run` 通过。探针暴露的 JSON 解析损坏由 `_util` 容错 + `_is_empty_events` 纳入 recheck 修复。探针 36 次延迟已记录（正例 median 33.3 s / p95 45.0 s；负例 median 16.8 s / p95 22.9 s，口径未注明，不与主口径横比）。7 条主回归 7/7、0 多抽、`error=None`；全流程延迟 median 11040 ms（7×1，非抽取节点口径）。id 4 的周次歧义仍未写入 `ambiguity`。E1b 后续已启动并完成 E1b-1，但操纵失败（见下）；E0 的 21 次抽取节点同口径延迟仍待补。原始数据：[probe_e01_v3-opt-e01.csv](v3/probe_e01_v3-opt-e01.csv)；7 条主回归原始 CSV 在代码仓 `assets/data/main_regress_v3opt_e01.csv`，本仓库未直接校验该文件。

**问题**：id 7 是“公告型通知”，同时含“提交截止 10/20”“名单公布 11/7”“倒计时 3 天”。模型稳定判空，说明当前 Prompt 对“公告里的用户截止”召回不足。id 8 是“订购窗口 8/4–8/11”，同类风险。

> **历史假设（2026-10-19，已被探针验证）**：漏抽不是基础链路故障，而是“信息日期 / 名单公布不抽”规则在 deadline 型公告上被整段误用；探针确认这是通用偶发漏抽，不是 id 7 个例。
>
> 这条规则在 v3 和 v3-opt 中逐字相同，并非 v3-opt 新增；v3 在补充 B 的 id 7 上也不是 3/3（run1 多抽、run2 空返回、run3 输入缺失）。完整过程见 [E0.1-deadline召回专项.md](v3/v3.2/E0.1-deadline召回专项.md#51-闭环结果用户反馈-2026-10-19)。

**先诊断，不要直接加第二次 LLM 调用**：

1. 从 E0 日志取 id 7/id 8 每次的 `intent_raw`、`has_recordable_event`、`events`、`notes`、`error`。
2. 分类：
   - 意图 false → 意图节点漏判，抽取 Prompt 根本没跑；
   - 意图 true + `events=[]` + `notes` 为“无可记录事项” → 抽取 Prompt 召回问题；
   - 意图 true + `events=[]` + `notes` 为“未提供原文” → 输入绑定问题（E0 应已修）；
   - 意图 true + 抽取有事件但归一化为空 → `normalize_extraction` 问题。
3. 只有确认是第二类，才改抽取 Prompt；否则改对应节点，避免“加 recover 掩盖真正故障”。

**专项探针（与 7 条主回归分开）**：至少 8 条正例 + 4 条负例，每条 3 轮。正例覆盖提交、报名、缴费、订购、申请、公告型、过期型；负例覆盖名单公布、结果公布、活动开始、纯公告。探针只做诊断，不替换主测试集，不写成统计显著。

**Prompt 补丁（已验证，已并入主图配置）**：

```text
【deadline 召回补充规则】
1. 公告/通知里出现“提交 / 报名 / 缴费 / 订购 / 申请 / 注册”等用户动作，并给出“截止 / 前完成 / 窗口 / 之内”等时间边界时，必须抽成 deadline；即使整条文本看起来像通知、公告，或没有“请 / 需要 / 记得”等主语，也要抽。
2. “名单公布 / 结果公布 / 活动开始 / 晋级名单”等信息日期仍然只写 notes；但如果同一句还明确写了用户的提交/报名截止，提交/报名截止必须单独抽 deadline，不能因为同段有信息日期就整条判空。
3. 倒计时与明确截止日期不一致时，以明确日期为准，仍要抽 deadline，并在 ambiguity 说明；不得因为矛盾判空。
4. 截止日期已过期不等于不可记录：仍按原文输出 deadline，priority 用 null，并在 notes 或 ambiguity 标注“已过期”。
```

**恢复兜底（仅在前两步仍漏抽时启用）**：

- 触发条件必须同时满足：`events=[]` + 原文含“动作 + 截止”线索 + 含日期/时间表达；仅有“名单公布 / 结果公布 / 活动开始”不触发。
- 优先用代码节点 `deadline_guard` 做确定性触发（见 `v3/v3.2/deadline_guard.js`），不要在空输出时无条件再调一次 LLM。
- 若意图节点判 false 但 `deadline_guard.deadline_cue=true`，条件分支强制进入抽取；这是零额外 LLM 成本的一层兜底。
- 若抽取仍为空，再调用一次短 recover Prompt（只抽 deadline，max_tokens 建议 300–500，temperature 0），并记录触发率、恢复准确率和新增延迟；不能静默把空输出当“无可记录事项”。
- 如果暂时不做第二次调用，至少返回 `needs_confirmation: true` + `notes: "检测到截止信息但未抽取，请确认"`，避免用户看到错误的“没有事项”。

## 实验 E1b-1：max_tokens 2000 vs 1200（未采用；操纵失败）

- 日期：2026-10-19（用户反馈）
- 版本/条件：v3-opt + E0.1 补丁；火山方舟直连；抽取 LLM 单次调用口径（`latency_scope=extract_llm_e2e`）
- 模型：`doubao-seed-2-0-pro-260215`（非推理，thinking disabled）
- temperature：`0.1`（两组一致）
- max_tokens：控制组 C `2000`；变量组 V1 `1200`
- JSON 模式：开启
- Prompt 长度：两组相同；本实验不比较 Prompt
- 测试集：7 条（id 2–8）；测试基准日 `2026-10-18 09:00`
- 每条运行次数：3；C 21 次 + V1 21 次；42/42 `input_present=1`、`status=ok`、`finish_reason=stop`
- 操纵检查：**失败**。C 有 4/21 次 `completion_tokens > 2000`（最大 3085），V1 有 19/21 次 `> 1200`（最大 2909），且两组 `finish_reason` 全为 `stop`。设定上限没有约束生成，C/V1 很可能实际是同一有效配置；不能把差异归因于 max_tokens。
- 事件级（主事项是否抽出）：C 18/21；V1 20/21。失败运行：C id 2 run1、id 7 run2、id 7 run3；V1 id 7 run1，均为 0 事件。
- id 7：C 1/3、V1 2/3（合计 3/6）；id 8：两组均 3/3（`2026-08-11 23:59`，priority `null`）。
- id 4 周次歧义：两组共 6/6 都写出 `2026-10-22` 与 `2026-10-29`；与 7×1 主图 temp 0.0 的缺失相反，是温度假设的反向信号。
- 多抽：按“主事项 + 最多 1 条隐含 task”口径为 0；原始 `events_cnt=2` 在 C 有 3 次（id 2 run2/3、id 7 run1），V1 有 5 次（id 2 ×3、id 7 ×2）。严格“恰好 1 事件”口径需另算，评分表必须写明口径。
- 负例：仅 V1 的 N1–N4 各 1 次，0/4 误抽；控制组负例未运行，不能写“两组均零误抽”。
- 平均延迟：C 37911.7 ms（全 21 次）/ 42141.1 ms（非空 18 次）；V1 35861.9 ms（全 21 次）/ 37262.3 ms（非空 20 次）
- 中位延迟：C 34947 ms（全 21 次）/ 36198 ms（非空 18 次）；V1 36278 ms（全 21 次）/ 36418.5 ms（非空 20 次）
- p95：C 66866 ms、V1 46386 ms（均按全 21 次计；21 个样本的 p95 不稳定）
- 最大延迟：C 69690 ms；V1 59747 ms
- 与基线对比：不能与 E0 的 7×1 全流程 11040 ms、v3 的 21 次抽取节点 27202 ms 横比；本次只是同一渠道下 C vs V1。全部运行中位数 V1 反而慢约 1.3 s，非空输出中位数差约 0.2 s，**没有中位数收益**。p95/均值差异由 C 的少数长尾和样本量驱动，且操纵失败，不能写成 V1 降低尾延迟。
