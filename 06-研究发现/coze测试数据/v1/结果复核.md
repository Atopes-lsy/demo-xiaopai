## 4. 系统性发现

### F1 地点是当前最弱字段：4/7，57.1%

三个漏地点有共同模式：

1. 地点嵌在事件名称里（“宿舍卫生安全检查”里的“宿舍”）；
2. 地点嵌在长句里（“某市第一社会福利院开展……”）；
3. 地点后面跟着“具体教室待通知”，模型把整个 location 置空，而不是保留“某教学楼大教室”。

**产品影响**：确认卡片上地点缺失会直接影响用户信任；地点也是差异化字段。需要加一条明确规则：

> 原文出现机构名、楼名、园区名、房间名时，即使更细的房间待定，也要填写已知的最细层级；只有完全没有地点线索时才用 null。

### F2 时间：6/7，85.7%，但错误很典型

- “3:20”没有上午/下午，模型选了 03:20；年级会/上课/开会这类场景通常是下午，模型应该输出 15:20，并注明“原文未写上午/下午，按下午处理”。
- “下周四”存在 10/22 与 10/29 两种可能，模型静默选了 10/22，没有在 `ambiguity` 说明。

**产品影响**：时间错一次，用户就会开始怀疑所有自动排期。宁可输出“15:20（待确认）”，也不要静默给凌晨时间。

### F3 隐含任务要允许，但不能给硬截止

id 2 的“保持清洁”可以是建议任务，但模型把检查时间写成它的 deadline。更好的输出是：

```json
{
  "title": "保持宿舍清洁，清理公共区域垃圾，移除违规电器",
  "type": "task",
  "deadline": null,
  "priority": null,
  "dependencies": [],
  "ambiguity": "建议任务；原文只要求在检查前保持清洁，没有单独截止时间"
}
```

**产品影响**：建议任务可以帮用户提前准备，但不能伪造硬约束；否则自动排期会把用户的时间排满。

### F4 信息日期不是用户 DDL

id 7 的“11 月 7 日名单公布”被抽成 event。公告里的“公布名单 / 公布结果 / 活动开始”只有在对用户有行动要求时才是事项；否则只应留在 notes。

### F5 延迟

- 平均 8078 ms，中位数 6923 ms，最大 15319 ms（id 2 长通知）。
- 8 秒对“粘贴后等结果”的体验偏慢；15 秒在微信小程序里可能触发超时或让用户放弃。
- 建议：限制输入长度（MVP 2000 字以内）、长通知先截取关键段、意图判断用更轻的模型、抽取节点用更快的模型；正式产品考虑异步任务 + 进度提示。

### F6 intent 100% 不能说明“不会误抽”

这 7 条都是需要记录的通知，没有闲聊、广告、问用法、表情等负样本。`intent_ok=7/7` 只说明这 7 条没有被漏掉，不能说明系统不会把闲聊抽成事项。要验证误抽，至少补 5–10 条负样本。

### F7 有些指标是“空过”，不是真的测到了

- `estimate_ok=7/7`：主事项都是 event / deadline，`estimate_min` 本来就该是 null；没有“task + 明确估时”的样本。
- `type_ok=7/7`：只有 event / deadline，没有真正的 task 主事项；task 分类没有被充分测试。
- `dependency_ok=7/7`：原文都没有显式依赖；没有真正测到依赖抽取。
- 因此不要把这几个 100% 当作模型能力结论，只能说明这批样本里没有暴露问题。

## 5. 新工作流 Prompt 已经补的规则

[Coze-小排工作流提示词.md](../../../07-MVP定义/Coze-小排工作流提示词.md) 已经加入：

- 地点：机构/楼名/园区/房间名优先保留最细已知层级；
- 时间：只有日期时按语义用 23:59 或 null，不伪造 00:00；
- 时间：`3:20` 这类没有上午/下午的时间，按场景判断并在 `ambiguity` 说明；
- 隐含任务：允许 task，但不给新的硬截止；
- 依赖：只抽原文明确先后关系；
- 信息日期：名单公布/结果公布不抽成用户 event/deadline；
- 优先级：event 一律 null；deadline/task 没有依据时 null；
- 估时：只有 task 估时，缺失时 `estimate_min=null` 并进入 `missing_fields`。

这 7 条是用 v1 prompt 跑的；新 workflow prompt 还没有重跑。下一步建议先用同一批 7 条跑新 prompt，比较错误类型是否减少，再扩到 30 条。
