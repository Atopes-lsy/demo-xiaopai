# Coze 抽取测试研究发现（收口版）

> 测试周期：2026-10-18 至 2026-10-19。测试对象：小排「群消息/项目说明 → 结构化事项」抽取链路。
>
> 样本：7 条脱敏真实通知（id 2–8），每轮按「通过条数 / 7」记录。**7 条只用于发现错误模式，不用于估计总体准确率。**
>
> 收口原因：Coze 进阶版 3 万积分已用完，Coze 上的测试到此结束。本文汇总已经跑过的版本、失败模式、产品启示和不能再下的结论；后续验证应转到本地/后端评测，不依赖 Coze 额度。

## 0. 一句话结论

**Coze 测试证明：这条抽取链路在 7 条真实通知上可以跑通，但「单次 7/7」不能当成产品准确率。** 真正有价值的发现是四类风险：多轮运行不稳定、输入绑定会丢失、公告型 deadline 会漏抽、延迟口径混乱导致无法比较。Coze 适合做原型和发现错误，不适合作为生产验证或最终评测平台。

## 2. 主要研究发现

### F1 抽取链路可行，但单次 7/7 明显高估稳定性

**证据**

- v3 单次 7×1 达到事件、时间、地点、优先级 7/7，幻觉 0/7。
- 同一 v3 Prompt 的 7×3 完整重跑只有 15/21 端到端通过、15/17 非空事件级通过；只有 id3/4/5/8 达到 3/3。
- v3-opt+E0.1 的 7 条主回归是 **7×1**，不是 3 轮稳定性；E1b-1 在直连 temp 0.1 下 C 18/21、V1 20/21，id7 合计仅 3/6。

**说明**

链路、字段 schema、Prompt 基本可行，但“每次都能抽出”不成立。单次 7/7 只能说明这一轮没有暴露错误，不能说明错误率低。

**产品影响**

- 不能把“全自动、零确认”作为 MVP 前提；确认/编辑/撤销仍是必需的安全垫。
- 评测至少要看 3 轮和逐次失败原因，不能只看一次总分。
- 对外表述必须带样本量，例如“7 条回归样本中 7/7”，不能写“准确率 100%”。

### F2 v1→v3 的收益主要来自字段规则，不是模型升级

**证据**

- v1→v3：地点 4/7→7/7、时间 6/7→7/7、优先级 4/7→7/7（严格复核）、幻觉 2/7→0/7。
- 修复手段都是 Prompt 规则：已知地点层级保留、裸时间 `3:20→15:20`、信息日期只写 notes、P3 必须有原文依据、输出前自检。
- 模型属性已确认：`doubao-seed-2-0-pro-260215` 是非推理模型（thinking disabled）；没有做过“换模型”的对比。

**说明**

在这 7 条上，规则迭代是有效的；但不能把改善归因于“换了更强的模型”或“模型能力提升”，因为没有模型对照。也不能把 v1→v3 的分数差写成严格同条件的因果结论，因为版本间还叠加了其他规则和运行条件变化。

**产品影响**

- 先把字段规则、标注口径和失败样本库做扎实，再谈换模型。
- 模型升级必须另做同测试集、同 Prompt、同参数的单变量实验；目前没有这类证据。

### F3 输入绑定和解析失败，是比“模型漏抽”更靠前的工程问题

**证据**

- v3 的 7×3 重跑 B 中，3/21 次输入未传入，模型返回“未提供原文”；这不是模型漏抽，而是工作流输入变量没有传到位。
- v3-opt 增加 `validate_input` 后，E1b-1 两组 42/42 次 `input_present=1`。
- 但 E1b-1 控制组 id7 run2 仍出现“未提供待抽取的通知原文”，而该次 `input_present=1`：说明“模型声称没收到原文”还可能单独发生，不能只靠输入校验兜底。
- 探针还暴露过 JSON 局部损坏；已用 `_util` 容错 + `_is_empty_events` 将解析失败纳入 recheck，而不是直接当“无可记录事项”。

**说明**

用户看到的“没识别出来”至少有三类原因：输入没传到、JSON 解析失败、模型真的判空。三类的修复位置完全不同。只改 Prompt 会掩盖前两类。

**产品影响**

- 生产后端必须做输入回执、JSON 容错、错误分类和重试；解析失败不能静默返回空事件。
- 日志至少记录：输入是否存在、模型原始输出、解析状态、节点错误、使用的 Prompt/模型/参数。
- 前端要有“没有收到内容 / 识别失败 / 确实没有事项”三种不同状态，不能都显示成“没有可记录事项”。

### F4 公告型 deadline 是高风险长尾，补丁有效但不够稳

**证据**

- id7（作品提交截止）和 id8（教材订购窗口）在早期版本中被稳定判空；原因是“名单公布/信息日期不抽”的规则在公告型文本上被整段过度应用。
- E0.1 探针确认这是通用偶发漏抽：P8 1/3、P6 2/3。加 deadline 召回补丁后，P1–P8 正例均 ≥2/3（P3 2/3），负例 0/12；主图 id7/id8 均 3/3，7 条主回归 7/7。
- 但 E1b-1 在火山方舟直连、temp 0.1 下，id7 只有 3/6；主图 temp 0.0 的 E0.1 id7 是 3/3。渠道、temperature、Prompt 运行状态不同，不能直接归因温度，但说明“补丁通过一次探针”不等于长期稳定。

**说明**

deadline 是用户最不能漏的字段，而公告型文本恰好容易触发“信息日期不抽”的误判。Prompt 补丁能修，但依赖模型每次都正确执行规则。

**产品影响**

- 需要确定性的 deadline 线索检测/guard：动作词 + 时间边界 + 日期命中时，即使抽取为空也要触发复查或提示确认，不能直接显示“没有事项”。
- 负例（名单公布、结果公布、活动开始）要继续保留，防止 guard 引发误抽。
- 对 id7/id8 这类文本建立专项回归，不要只放在 7 条总表里看总分。

### F5 多抽的判定依赖产品定义，不能只看 `events_cnt`

**证据**

- v3 的 7×3 重跑 B 有 2/21 次多抽：id2 run2、id7 run1；把隐含准备任务拆成了独立事件。
- v3-opt 加了“隐含/建议 task 最多 1 条”的规则后，7 条主回归 0 多抽。
- E1b-1 中仍常见 `events_cnt=2`：C 3 次、V1 5 次，内容都是“主事项 + 1 条隐含 task”。按“最多 1 条隐含 task”口径不算多抽；按“恰好 1 个事件”的严格口径则要另算。

**说明**

同一个输出，评分口径不同会得到不同结论。当前 7 条里没有真正的多事项项目说明和显式依赖样本，多抽/漏抽的边界还没有被充分覆盖。

**产品影响**

- 先定义“什么算一个可记录事项”，再写评分表；评分表要写明隐含 task 是否计入。
- 确认卡片允许删除多余卡片；低置信度的隐含 task 默认不直接保存，或标记为建议。
- 扩样时补 3–5 条真实 task、显式依赖和多事项项目说明，否则“估时/依赖正确率 100%”只是空过。

### F6 延迟不能跨口径比较，Coze 阶段没有拿到有效优化结果

**证据**

| 口径 | 典型结果 | 能说明什么 |
|---|---:|---|
| 旧单次：整个工作流，Coze 托管，抽取 temp 0.0 | 平均 10268 ms / 中位 10668 ms | 用户感知的早期全流程方向性参考 |
| v3-opt+E0.1 主回归：整个工作流，Coze 托管，7×1 | 中位 11040 ms（min 9914 / max 16820） | 全流程 7 次，不是抽取节点，也不是 3 轮稳定性 |
| v3 21 次：仅抽取节点，火山方舟直连，temp 0.1 | 平均 26385 ms / 中位 27202 ms | 抽取调用本身可能很慢；不含意图/normalize |
| E0.1 探针：口径未注明 | 正例中位 33.3 s；负例中位 16.8 s | 只能作探针内部参考 |
| E1b-1：仅抽取调用，火山方舟直连，temp 0.1 | 全部运行中位 C 34947 / V1 36278 ms；非空中位 36198 / 36418.5 ms | 没有中位数收益；参数未生效，不能归因 |

**说明**

这些数字的计时对象、渠道、temperature、模型个数都不同，不能横比，也不能说“v3 比 v2 慢”或“抽取优化后变快”。Coze 阶段唯一能确认的是：抽取 LLM 调用是一个显著耗时点，且全流程到结果不是“即时”体验。

**产品影响**

- 先定义用户感知的延迟 SLO（端到端，而不是抽取节点），再优化。
- 保留 loading/进度反馈；如果端到端长期超过几秒，需要考虑异步、分段返回或更快的路由模型。
- 后续优化必须记录 `latency_scope`、渠道、temperature、输入是否存在、是否包含意图/normalize；否则数据不可用。

### F7 参数、温度、模型问题尚未闭环，不能据此改生产配置

**证据**

- E1b-1 想比较 `max_tokens 2000` vs `1200`，但两组都有超过各自上限的输出且 `finish_reason=stop`：V1 19/21 次 >1200（最大 2909），C 4/21 次 >2000（最大 3085）。参数没有实际生效，实验不能做归因。
- id7 在直连 temp 0.1 下 3/6；但 id4 周次歧义在同样的 6 次里 6/6 都写对了，而主图 temp 0.0 的 7×1 反而缺失。温度假设存在反向证据，且渠道/Prompt 状态混杂。
- 控制组 id7 只有 1/3，未达到 E1b 工单要求的 3/3；负例只跑了 V1 一侧。即使忽略参数未生效，采用条件也不成立。
- 模型已确认是非推理模型，没有做过模型替换对照；不存在“换成非推理模型后提升”的实测结论。

**说明**

目前没有足够证据支持改 temperature、max_tokens 或模型。E1b-1 的质量差 20/21 vs 18/21 只能当重复运行噪声。

**产品影响**

- 生产配置维持现状；不要因为一次实验改参数。
- 若继续验证温度：同渠道、同 Prompt、同输入，temp 0.0 vs 0.1，先 7×3×2，必要时对 id7/id2 定向追加；同时把 id4 ambiguity 作为观测项。
- 任何模型网关参数都要先在请求层做“操纵检查”（例如把上限设到很小，确认输出真的被截断），否则不要跑正式实验。

## 3. 研究方法的三个教训

1. **原型平台和评测平台要分开。** Coze 适合快速接线和看错误，但额度、日志、参数透传和批量运行不适合长期评测。本轮 3 万积分用完后无法补跑，说明评测应放在本地脚本/后端，Coze 只保留为演示原型。
2. **单次 7/7 不能替代多轮回归。** v3 单次 7/7，但同一 Prompt 的 7×3 只有 15/21 端到端；失败里还有输入未传入和隐含任务多抽，不是同一类问题。
3. **口径要写在结果前面。** 延迟是“全流程还是抽取节点”、渠道是“Coze 托管还是方舟直连”、temperature 是 0.0 还是 0.1、`events_cnt` 是否等于空输出，这些都会改变结论。先定义口径，再跑数据。

## 4. 哪些结论能写，哪些不能写

| 可以说 | 不能说 |
|---|---|
| 7 条回归样本中，v3 单次事件/时间/地点/优先级 7/7，幻觉 0/7 | “抽取准确率 100%”或“总体准确率 80%+” |
| v3 的 7×3 重跑中，15/21 端到端、15/17 非空事件级通过 | “3 轮质量稳定 7/7” |
| 公告型 deadline 曾稳定漏抽，补丁后探针通过、主图 id7/id8 3/3 | “deadline 问题已彻底解决” |
| 输入未传入 3/21、隐含任务多抽 2/21，已加校验/规则 | “所有漏抽都是模型能力问题” |
| max_tokens 在本次请求里未生效，实验不能归因 | “max_tokens 参数无效”或“1200 更快” |
| 全流程约 10–11 s、抽取直连约 26–36 s，但口径不同 | “端到端 26 s”或“优化后变快” |
| 7 条样本用于发现错误模式，不做统计外推 | “准确率 85.7%”这类总体比例结论 |

## 5. 可写进面试/简历的表述

**简洁版**

> 用 7 条脱敏真实群通知搭建回归集，完成 v1→v3 的 Prompt 迭代，并额外做 7×3 完整重跑。单次 v3 达到事件/时间/地点/优先级 7/7、幻觉 0/7，但多轮重跑只有 15/21 端到端通过，暴露了 3 次输入未传入和 2 次隐含任务多抽；进一步用 8 条正例 + 4 条负例的探针定位公告型 deadline 漏抽，补丁后主图 id7/id8 3/3、负例 0/12。最后做了 max_tokens 参数实验，但发现参数未真正绑定请求（两组均有超过上限的输出且正常结束），因此没有把它写成优化成果，而是保留了操纵失败的结论。

**这段能体现的能力**

- 不是只报喜：能区分“模型错”和“工作流错”。
- 会做小样本回归、探针诊断、单变量实验和操纵检查。
- 知道延迟口径不能混，知道 7 条不能外推。
- 能在证据不足时停手，而不是为了结果继续调参。

## 6. 后续（不依赖 Coze）

1. **把评测搬出 Coze**：用本地脚本或后端调用同一模型/网关，固定 Prompt 版本、基准日、输入和参数，逐次保存完整输出。现有的 v1/v2/v3、E0.1、E1b-1 CSV 作为历史基线保留。
2. **扩样**：从 7 条扩到 20–30 条，优先补公告型 deadline、多事项项目说明、真实 task、显式依赖和 5–10 条负例；扩样前不写总体准确率。
3. **修可靠性**：输入回执、JSON 容错、deadline guard、空输出分类、错误重试和日志。Coze 测试已经证明这些是产品问题，不只是 Prompt 问题。
4. **延迟**：先定端到端 SLO 和节点埋点，再决定是否做 T2–T5；不要把抽取节点耗时当端到端。
5. **参数实验**：只在参数能实际绑定请求时重做；温度实验优先于继续降 max_tokens。
6. **用户验证**：用现有 7 条识别结果做确认卡片/Wizard-of-Oz pilot，先看用户是否愿意粘贴、是否愿意修改、是否信任结果；不要只测模型分数。
