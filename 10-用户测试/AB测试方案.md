# A/B 测试方案：课旁（课表 + 日程 + DDL）

## 1. A/B 测试在产品经理职责里是做什么的

A/B 测试不是“上线后看看数据”，而是一个**随机对照实验**：

- 把用户随机分成两组或多组；
- 每组看到不同版本（A/B）；
- 在相同时间内比较核心指标；
- 用统计结果判断“这个改动是否真的带来了提升”，而不是靠感觉或个别用户反馈。

产品经理在其中的责任：

1. **提假设**：改什么、为什么改、预期影响哪个指标；
2. **定指标**：一个主指标 + 若干护栏指标，提前写清楚；
3. **算样本**：需要多少用户、跑多久，避免“跑两天就下结论”；
4. **协调**：设计、开发、数据、运营一起把实验做出来；
5. **守规则**：随机分组、不中途偷看、不频繁换体验、不伤害用户；
6. **做决策**：上线、回滚、继续迭代，或者结论不显著就放弃；
7. **复盘**：把结论写回 PRD/研究发现，避免重复试错。

一句话：**A/B 测试是产品经理用来把“我觉得”变成“数据表明”的工具，但它只在样本足够、指标清楚、改动可逆时才有意义。**

## 2. 这个项目现在该不该做 A/B 测试

### 现在（研究/MVP 前）：不做正式 A/B

原因：

- 还没有真实用户和流量；
- 核心问题（用户是否愿意转发、识别是否准确）用问卷、访谈、原型测试更便宜；
- 样本量不够时，A/B 结果不可信，容易误导。

这一阶段用：

- 用户访谈（已有提纲）；
- 问卷（12 题版）；
- 可点击原型测试；
- Wizard-of-Oz / Concierge MVP（人工模拟识别，见低代码方案）；
- 5 名用户的可用性测试。

### MVP 内测期：可以做“小流量实验”，但要谨慎

建议门槛：

- 至少 **500–1,000 名周活跃用户**；
- 每个实验组至少 **200–500 个关键事件**；
- 主指标有稳定埋点；
- 实验周期至少 **1–2 周**，覆盖一个完整的课表周。

低于这个量级，优先做**前后对比 + 用户测试**，不要硬做 A/B。

### 上线后：按“实验日历”滚动做

每月 1–2 个实验，优先做影响核心链路（导入 → 识别 → 确认 → 保存 → 回访）的改动。

## 3. 候选实验清单

### 实验 1：首次建课表的入口

**假设**：对新生来说，“从微信聊天记录选文件”比“拍照识别”更短，能提高首次建表完成率。

| 组 | 入口 |
|---|---|
| A | 首页主按钮「从聊天记录导入课表」 |
| B | 首页主按钮「拍照识别课表」 |

- 主指标：首次建表完成率
- 护栏：从进入到建表完成的时间、导入失败率、用户修改课程数
- 决策：完成率提升 ≥ 5 个百分点且失败率不升高 → 上线；否则保留双入口

### 实验 2：识别结果的确认方式

**假设**：默认展开可编辑字段，比“一键确认”更能减少后续错误，但会增加确认时间。需要找到平衡。

| 组 | 确认卡片 |
|---|---|
| A | 一键确认 + “修改”按钮 |
| B | 默认展开时间/地点/类型，可直接改 |

- 主指标：确认保存率
- 护栏：确认耗时、修改率、7 日内纠错率
- 决策：保存率不降、确认耗时中位数 ≤ 10 秒 → 选 B；否则选 A

### 实验 3：课表与日程的首页布局

**假设**：同屏叠加比 Tab 切换更能让用户看到“课表旁边的安排”，提高回访。

| 组 | 首页 |
|---|---|
| A | 课表为底，日程/DDL 叠加在同一屏 |
| B | 课表 / 日程两个 Tab |

- 主指标：7 日留存
- 护栏：日程创建数、页面停留、DDL 逾期率、用户投诉
- 决策：留存提升 ≥ 3 个百分点且逾期率不升高 → 上线同屏

### 实验 4：DDL 的视觉呈现

**假设**：顶部“本周 DDL”栏 + 红色截止条，比普通列表更能减少逾期。

| 组 | DDL 呈现 |
|---|---|
| A | 顶部本周 DDL 栏 + 逾期标红 |
| B | 与日程混排的普通列表 |

- 主指标：DDL 按时完成率
- 护栏：误触率、用户主动关闭提醒的比例、主观焦虑反馈
- 决策：按时完成率提升且关闭比例不升高 → 上线 A

### 实验 5：有限提醒额度怎么花

**假设**：把有限的一次性订阅提醒优先给“最近截止的 DDL”，比平均分配更能提升完成率。

| 组 | 提醒分配 |
|---|---|
| A | 优先最近 3 个 DDL |
| B | 优先最近 3 个日程 |

- 主指标：提醒点击率 / DDL 完成率
- 护栏：订阅授权率、额度耗尽速度、用户关闭订阅比例
- 决策：完成率提升且关闭率不升高 → 上线 A

### 实验 6：隐私说明的写法

**假设**：在转发入口明确写“只处理你主动转发的这一条，不读取聊天记录”，能提高首次转发率。

| 组 | 入口文案 |
|---|---|
| A | 简短版：“转发一条，识别一条” |
| B | 解释版：“只处理你转发的这条消息，不读取聊天记录” |

- 主指标：首次转发完成率
- 护栏：入口跳出率、后续 7 日转发次数
- 决策：完成率提升 → 用 B；否则用更短的 A

> 备注：实验 6 同时也是合规要求的一部分——隐私告知必须在入口处可见，不能只放在隐私政策里。A/B 只能比较“怎么说”，不能比较“说不说”。

## 4. 实验前必须写清楚的一张表

每个实验启动前，产品经理填完这张表，数据/开发再动手：

| 项目 | 内容 |
|---|---|
| 实验名称 | 例如 `import_entry_v1` |
| 假设 | 一句话，可证伪 |
| 变体 | A 是什么、B 是什么 |
| 随机单元 | 用户（openid 哈希） |
| 样本量 | 每组多少人、怎么算的 |
| 主指标 | 只能一个 |
| 护栏指标 | 2–3 个 |
| 实验周期 | 开始/结束日期 |
| 决策规则 | 提升多少上线、下降多少回滚、不显著怎么办 |
| 埋点 | 曝光、点击、完成、失败、修改 |
| 风险 | 是否影响隐私、提醒额度、核心体验 |

## 5. 技术怎么落地（微信小程序）

微信小程序没有像 Web 那样成熟的官方 A/B 平台，建议：

1. **服务端分组**：用户首次进入时，用 `openid` 哈希取模分组（如 `hash % 100`），把组别写入用户表；
2. **配置开关**：后端下发实验配置，小程序按配置渲染 A/B；
3. **曝光埋点**：用户真正看到实验版本时上报 `exposure`，避免把“没看到”的用户算进分母；
4. **事件埋点**：导入完成、识别成功、确认保存、7 日回访等关键事件；
5. **数据看板**：先用服务端日志 + Metabase/自建看板，量起来后再考虑 GrowingIO/神策/腾讯有数；
6. **停止规则**：样本比例失衡（SRM）、护栏指标显著恶化、实验造成投诉，立即停止。

最小数据模型：

```text
experiment: id, name, status, start_at, end_at, variants
assignment: user_id, experiment_id, variant, assigned_at
exposure: user_id, experiment_id, variant, event, occurred_at
metric_event: user_id, event_name, properties, occurred_at
```

## 6. 常见坑

- **样本不够就下结论**：小样本的波动会被误读成“显著提升”。
- **中途偷看**：每天看一次 p 值，看到显著就停，会抬高假阳性。
- **指标太多**：每个实验只留一个主指标，其他都是护栏。
- **忽略护栏**：转化率涨了，但识别错误率、投诉、卸载也涨了，不能上线。
- **新奇效应**：老用户对新界面的短期好奇，不代表长期留存。
- **网络效应/共享**：如果后续做班级共享，用户之间会互相影响，普通 A/B 不适用。
- **把相关当因果**：A/B 的价值在于随机分组，不是“用了新版本的人留存更高”。

## 7. 这个项目的实验节奏

| 阶段 | 做什么 | 不做什么 |
|---|---|---|
| 现在（研究） | 访谈、问卷、原型测试、Wizard-of-Oz | 不做正式 A/B |
| MVP 内测（< 500 用户） | 前后对比、5–10 人可用性测试、错误分类 | 不做统计显著性实验 |
| 500–1,000 周活 | 先跑 1 个低风险实验（入口文案/确认方式） | 不同时开 3 个以上实验 |
| 1,000+ 周活 | 每月 1–2 个实验，建立实验日历 | 不在核心链路上做高风险实验 |

---

## 8. 一句话总结

**现在用低代码和人工模拟验证“值不值得做”，MVP 用可用性测试验证“能不能用”，有流量之后再用 A/B 测试验证“哪个版本更好”。** 顺序不能反。
